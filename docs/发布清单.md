# 发布清单（Release Checklist）

> 每次改动**收尾时逐条过一遍**。任一条不过 → **不推送**。
> 背景：2026-10-09 阶段五改了用户可见界面，却漏了 bump 版本 + changelog，
> 线上更新弹窗仍显示旧版本说明（详见 `../docs/踩坑记录与应对措施-2026-10-10.md` K7）。

---

## 一、代码改动

- [ ] 每个修复/功能**独立 commit**，消息含「**问题 / 思路 / 验证**」三要素
- [ ] 不为了过测试而改断言 / 删失败用例

## 二、版本与更新日志（**用户可见改动必做**）

- [ ] `frontend/src/changelog.ts`：`CURRENT_VERSION` 升位 + **首条条目**为新版本
      （有门禁锁「首条条目 === CURRENT_VERSION」「标题不含技术术语」）
- [ ] `frontend/src/changelog.ts` 首条条目含**至少一条 user 级**文案（弹窗不空）
- [ ] `backend/src/main/resources/application.yml` 的 `app.info.version` 同步
- [ ] `backend/pom.xml` 的 `<version>` 同步
- [ ] 三处版本号**一致**（`grep -rn "旧版本号"` 确认无残留）

> 只改内部实现、用户完全无感的改动，可不升版本——但**界面/文案/交互有任何变化就必须升**。

## 三、本地回归（全绿才继续）

> **一条命令跑完下面前三项**：`node scripts/verify-release.mjs`
> （顺序固定、任一失败立即中止并返回非 0；沙箱内会自动识别 `safe-delete` 环境守卫
> 并改用仓库外临时目录重试，因此沙箱内外都能拿到「构建到底能不能过」的结论。）
>
> **为什么固化成脚本**：2026-10-12 发 v1.66.20 时，交给验证方的任务说明里**漏了 `vite build`**。
> 后果不是「少跑一个检查」——Cloudflare Pages 的部署**依赖构建**，构建若失败，
> 线上表现与「平台没触发构建」**完全一样**（都是「push 了但站点不动」），
> 排查成本翻倍。清单靠人逐条记迟早会漏，故落成脚本。

- [ ] 前端：`npx vue-tsc --noEmit` → 0 error
- [ ] 前端：`npx vitest run` → 全通过（含 `designGuards` + `changelog` 门禁）
- [ ] 前端：`npx vite build` → 成功
- [ ] 后端：`mvn test` → 全通过（**测试通过 ≠ 打包成功**，构建也跑）
- [ ] 若改了依赖：确认无新增 high 级漏洞（CI 的 `npm audit --audit-level=high` 会拦）

## 四、推送与部署

- [ ] `git -C interview-guide push origin main`
      （后端 Render `autoDeployTrigger: commit`、前端 Cloudflare Pages 自动构建）
- [ ] CI 转绿（`gh api repos/.../actions/runs`）

## 五、部署验证（**顺序不能颠倒**）

> **一条命令验证线上是否真的部署了**：`node scripts/verify-release.mjs --live`
> （无缓存拉 `index.html` → 取入口 chunk → 搜 `CURRENT_VERSION`；失败时直接打印
> 排查顺序与「空提交重触发」的处置。）
> ⚠️ 线上入口 chunk 名**不等于**本机 `vite build` 的 chunk 名（CF 项目侧有
> `VITE_API_BASE_URL` 等环境变量会改变内容哈希）→ 判据用「chunk 里是否含 `CURRENT_VERSION`」。
> ⚠️ **push 成功 ≠ 平台触发构建**：2026-10-12 实测 CF Pages 18 分钟未构建，
> 处置 = `git commit --allow-empty && git push`（约 1.5 分钟生效）。

- [ ] **先**确认部署状态到 `success`——认准是哪个 deployment（`sha` + `environment`）
- [ ] ⚠️ Render 免费层**新实例通过健康检查前，旧容器继续服务**（约 5–8 分钟）；
      这期间探测**必然看到旧行为**，**不要**据此判定部署失败
- [ ] **再**对线上做**确定性指纹**复验：用「新代码引入的行为」（某文案 / 某 HTTP 码），
      **不要**看版本号接口（可能被缓存/覆盖/延迟）
- [ ] 前端指纹：从 `offergo.pages.dev/sw.js` 取 chunk 名 → 抓 `assets/*View-*.js` 搜关键词
- [ ] 后端指纹：`/api/info`、`/actuator/info`（⚠️ `buildDate` 是**运行当天**，不能判断镜像新旧）

## 六、收尾

- [ ] 线上前后端版本/行为一致
- [ ] 如遇坑，回填 `docs/踩坑记录与应对措施-*.md`
- [ ] 外层仓库（无远端）如有需要，本地 commit 留档

---

## 一句话记忆

**改了用户可见的东西 → 升版本(三处) + 写 changelog + 全量回归 → push →
等部署 success → 用确定性行为验线上。**
