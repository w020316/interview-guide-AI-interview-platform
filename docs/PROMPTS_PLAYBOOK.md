## 一、提示词 A：全面质量评估与修复（代码审查 + 测试 + 页面检查）

```text
对当前项目（Spring Boot 3 + Spring AI 1.0.0 后端 / Vue 3 + TS + Vite 前端）执行全面质量评估与修复，分四个阶段：

【阶段1：代码审查】
- 范围：backend/src/main/java 全部 Service/Controller/Config/security，frontend/src 全部 views/components/utils/api
- 重点：逻辑错误、性能瓶颈（N+1/重复查询/无界缓存）、安全漏洞（越权/注入/敏感信息泄露/认证绕过）、
  编码规范（命名/注释完整性/魔法值/重复代码）
- 工具：静态分析（如可行用 mvn compile -X / vue-tsc 严格模式辅助），逐文件记录问题
- 输出：问题清单，每条含 文件路径+行号、问题描述、严重级别（P0阻断/P1严重/P2一般/P3建议）、修复建议

【阶段2：问题修复】
- P0/P1 100% 修复；P2 修复率 ≥90%；P3 列入 backlog 不阻塞
- 每个修复独立 commit（类型(范围): 描述），commit body 含问题/思路/验证方法
- 修复后全量回归：后端 mvn test（当前基线 264 个测试全过，不得减少）、前端 npx vitest run（基线 220 全过）+ vue-tsc 0 错误
- 涉及 SQL/实体变更时同步 SchemaInitializer 与 schema.sql，并确认 PostgreSQL 兼容（H2 本地通过≠生产通过，
  禁止 @Query 中 ":param IS NULL" 写法）

【阶段3：页面检查】
- 用浏览器自动化实测 4 种分辨率：1920×1080 / 1366×768 / 768×1024 / 375×667
- 检查：布局塌陷、横向滚动、导航溢出、深色模式一致性、加载态/空态/错误态完整
- 输出：页面检查报告（页面×分辨率矩阵 + 截图）+ 修复清单

【阶段4：交付报告】
- 功能清单（按模块标注：稳定/本次修复/新增/backlog）
- 测试结果（单测/集成/页面检查，通过/失败数）
- 问题修复记录（问题→方案→状态→验证）
- 遗留风险与建议

约束：一次对话只做一个阶段，每阶段结束先给我确认再进入下一阶段；
不得为凑指标修改测试断言或删除失败测试；所有修复必须真实可验证。
```

**基线数据**（2026-09-10）：后端 264 测试、前端 220 测试、vue-tsc 0 错误、版本 1.23.0。

## 二、提示词 B：真实用户体验评估（浏览器代理实测）

```text
以真实用户视角对 https://interview-guide-ai-interview-platform.pages.dev 做体验评估，
用浏览器自动化（可先注册测试账号）完整走通以下 3 个核心场景并记录：

【场景】
1. 新用户旅程：注册 → 登录 → 上传/粘贴简历 → 查看分析结果
2. 模拟面试旅程：创建会话 → 生成题目 → 答题 → 查看评分与复盘报告
3. 求职辅助旅程：招聘广场筛选岗位 → 进入智能体对话"找XX的岗位" → JD 岗位分析

【每个场景记录】
- 完整操作路径（页面/点击序列）与各步耗时
- 问题点：功能异常 / 操作繁琐 / 反馈不及时 / 文案不清，标注时间戳与重现步骤
- 截图佐证（每场景至少 2 张关键界面）

【量化评估】
- 用 SUS 量表（10 题标准问卷，自评）给出基线分；目标 ≥80 分，先记录当前分
- 任务完成率：3 场景是否可无障碍走通

【输出】
- 体验评估报告：旅程图（文字版）、问题清单（按 体验/流程/性能/文案 分组+优先级）、
  部分满足的需求对照（对照 docs/ 下功能设计）、
  改进建议（问题→方案→预期效果→实现难度→优先级，≥5 条）、
  新功能建议 ≥3 条（价值/难度/优先级 → roadmap）
- 注意：报告基于实测事实，无数据的指标标注"待基线"，不编造数据
```

**执行建议**：本条适合让我用 browser-use 代理执行（可截图、计时）；或你自己人工体验后把记录发给我整理成报告。

## 三、提示词 C：新项目/新模块调研与方案（模板三修正版）

使用前把 `〔目标项目〕` 替换为实际内容（如："AI 简历优化工具""面试题库小程序"）。

```text
针对计划开发的〔目标项目〕，编码前完成调研与方案：

1. GitHub 调研：筛 3-5 个同领域高质量开源项目（优先 star>5k、近 3 月有更新），
   用 WebSearch/WebFetch 核实 star 数、最近提交、license，输出对比表：
   功能模块 / 架构 / 技术栈 / 社区活跃度 / 维护状况 / 许可证 / 部署复杂度
2. 深度分析：每项目优缺点、扩展性/可维护性/安全性/性能 1-5 分评分、
   与〔目标项目〕需求的契合度、SWOT 分析
3. 方案制定：功能模块划分与接口定义、架构图（含部署）、技术栈选型理由、
   核心功能实现思路、风险与应对；结合本项目已有能力判断可复用部分
   （如模型降级链、SSE 模式、JWT 认证、部署流水线）
4. 里程碑：阶段划分 + 每阶段交付物与验收标准（不写具体日期，按阶段交付）
5. 输出正式调研文档（含目录/引言/调研/方案/风险章节，数据注明来源链接），
   提交给我评审确认后方可开始编码
约束：所有数据注明来源，禁止编造 star 数/性能数据；调研先行、方案经我确认后再动代码。
```

## 四、使用说明

| 提示词 | 触发时机 | 前置条件 | 预计轮次 |
|--------|----------|----------|----------|
| A 质量评估 | 版本发布前 / 大改后 | 无 | 4 轮（每阶段 1 轮） |
| B 体验评估 | 版本发布前 / UI 改版后 | 后端非冷启动（先 ping /api/info） | 1-2 轮 |
| C 项目调研 | 立新项目 / 大模块立项前 | 明确〔目标项目〕一句话定义 | 2 轮（调研→方案确认） |

**建议执行顺序**：B（先拿到真实体验问题）→ A（带着问题做代码级修复）→ C（下一个迭代方向立项）。
