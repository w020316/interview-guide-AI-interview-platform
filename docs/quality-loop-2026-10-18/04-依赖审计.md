## 一、结论摘要

**一句话：前端是干净的（npm audit 与 OSV 双源均为 0），后端的问题不是"某几个包旧"，而是"整条 Spring Boot 3.3 维护线已经关闭"——182 个第三方构件中 28 个命中 97 条已收录 CVE（11 critical / 42 high），且其中约 20 条在 3.3.x 线上根本没有修复版本。**

三行要点：

1. **3.3.13 是 Maven Central 上 3.3 线的最后一个版本**（metadata 中不存在 3.3.14+），该线官方 EOL 为 **2025-06-30**，距今已 16 个月。Spring Framework 6.1.21 / Spring Security 6.3.10 / Spring Data 3.3.13 / Spring Boot 3.3.13 这一族漏洞，在 OSV 里只有 `last_affected`、**没有同线 `fixed`** —— 也就是说留在 3.3.x 上，这些洞是修不掉的。
2. **但有一大半可以"就地"消掉**：Tomcat 10.1.42→10.1.61、postgresql 42.7.7→42.7.14、jackson 2.17.3→2.18.11、logback 1.5.18→1.5.38、jsoup 1.18.3→1.23.2、spring-ai 1.0.0→1.0.9 都有**同一条大版本线内的修复版**，属"覆盖版本属性 + 回归"级别，不涉及框架迁移。
3. **前端不需要任何动作**：`npm audit`（官方源）0 漏洞；OSV 独立复核 549 个 lock 节点同样 0 命中。前端不是本轮风险点。

> ⚠️ 口径说明：本文所有 CVE 均来自 OSV/GHSA 的真实查询结果（`api.osv.dev`，2026-10-18 当次请求），severity 取自 GHSA 的 `database_specific.severity`。**没有一条 CVE 是凭版本号推断或凭印象写的。** 但"是否可被利用"一栏是静态代码/配置判断，不是渗透验证结果。

### 4.2 为什么这个"0"可信（三组对照实验）

| 实验 | 现象 | 说明 |
|---|---|---|
| `npm ping --registry=https://registry.npmjs.org` | `PONG 1877ms` | 官方源直连可用，不需要代理 |

| `npm audit --registry=https://registry.example.invalid`（负控） | **失败**：`502 Bad Gateway - POST https://registry.example.invalid/-/npm/v1/security/audits/quick` → `npm error audit endpoint returned an error` | 证明确实发生了真实网络请求，不是读缓存或静默跳过 |

## 五、离线 CVE 扫描可行性

### 结论

**当前环境做不了真正的离线 CVE 扫描。** 原因不是"难"，而是**三个必要条件一个都不具备**，且全都经过本机实测确认。

### 逐条证据

| 必要条件 | 检查命令 | 实际结果 | 影响 |
|---|---|---|---|
| OWASP dependency-check 插件本体在本地仓库 | `ls D:/xm/maven-repo/org/owasp` | **`NO_org/owasp`（目录不存在）** | `mvn -o dependency-check:check` 会直接因"插件无法解析"失败，与 NVD 无关 |
| NVD 数据缓存已就绪 | 检查 `%TEMP%/dctemp`、`~/.dependency-check-data`、`~/OWASP` | **三者均不存在（`NO_DC_DATA_DIR`）** | 即使插件在手，首次也必须联网同步 NVD 全量数据 |
| 其它离线扫描器可用 | `command -v osv-scanner / trivy / grype / syft` | **4 个全部 missing** | 没有可替代的现成二进制 |

### 关于 OWASP dependency-check 的具体门槛

1. **NVD API 2.0 需要 API Key 才有可用速率**：无 key 时限流为每 30 秒 5 次请求，同步全量 CVE 会耗时数小时且极易中途失败；有 key 也需先申请。
2. **首次同步体积与耗时较大**：dependency-check 除 NVD 外还要拉取多个生态的附加数据源。具体 GB 数与分钟数**本次未实测**（不允许下载、且无 key），因此不写具体数字，详见第七节。
3. **离线模式只对"第二次以后"有效**：`--offline` 的前提是数据目录已经填充完毕。所以在拿到一次完整同步之前，"离线扫描"这个选项根本不存在。

### 已验证可行的替代路径（本次就用了）

OSV API（`https://api.osv.dev`）——**免费、无需 API Key、按版本精确比对、支持批量**：

| 场景 | 查询数 | 耗时 | 结果 |
|---|---|---|---|
| 后端 Maven 构件批量 | 182 条（一次 `querybatch`） | **1.22 s** | 命中 28 个构件 / 107 条 |
| 前端 lock 全量批量 | 549 条（一次 `querybatch`） | **1.67 s** | 0 命中 |
| 单条公告详情 | 97 次 `GET /v1/vulns/{id}` | 合计约 1 分钟 | 拿到 severity / CVE 别名 / 分支修复版本 |

**建议把这条路径固化成 CI 步骤**：`dependency:tree` 导出坐标 → `querybatch` 比对 → 结果落盘做基线 diff。既不需要 NVD 全量库，也能做到"新增漏洞必报警"。

> 注：`api.osv.dev` 在本机**直连不可用**（curl 退出码 35，SSL 连接失败），需经系统代理 `127.0.0.1:7890`。`repo1.maven.org` / `search.maven.org` 同样需要代理。这一点在搭 CI 时要先解决。
