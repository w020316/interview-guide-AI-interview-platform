## 二、G5 · 账号可改密（新增功能）

### 2.1 问题原始描述

`AuthController` 只有 register / login / logout / me 四个端点，全后端检索 `reset / forgot / changePassword` 映射为 **0 命中**。用户一旦忘记密码，账号连同简历记录、投递台账、面试复盘、故事库**永久无法取回**。

### 2.2 技术方案

| 层 | 改动 |
|---|---|
| 后端 | 新增 `POST /api/auth/change-password`（凭原密码）；新增 `revokeCurrentToken()` 并从 `logout` 中抽出复用；新增按用户 5 次/小时限流（`app.auth.change-password-limit-per-hour`） |
| 前端 | `ProfileView.vue` 新增「账号安全」区块（原密码 / 新密码 / 确认）；成功后 `clearAuth()` + 跳登录页 |
| 版本 | `1.66.20 → 1.67.0`，三处同步（`changelog.ts` / `application.yml` / `pom.xml`） |

**四条安全约束及理由**（缺一即成为攻击面）：

1. **必须校验原密码** —— 仅凭 token 不足以改密；否则 token 被窃 = 账号被夺。
2. **按用户限流 5 次/小时** —— 改密接口等价于一个「校验原密码」的猜解点，而它不受 `/login` 的 IP+账号双维度锁定保护。
3. **复用 `PasswordPolicy`** —— 否则改密成为绕过注册弱口令校验的后门。
4. **改密后吊销当前 token** —— 「改密」的语义就是让旧会话失效；不吊销等于攻击者拿到 token 后改密也能继续用。

## 三、线上指纹复验抓到的真缺陷（v1.67.1）

> 这条值得单独成节：**它证明「本地全绿 + 部署 success」不等于「行为正确」**。

### 3.1 现象

v1.67.0 部署 success 后，执行确定性指纹复验：

```bash
curl -X POST https://interview-guide-backend.onrender.com/api/auth/change-password \
  -H "Content-Type: application/json" -d '{"oldPassword":"x","newPassword":"y"}'
# 期望：HTTP 503（未认证）
# 实际：HTTP 200 + {"code":400,"message":"新密码长度需 6-64 字符"}
```

### 3.2 根因

Spring Security 的 **`AnonymousAuthenticationToken`**：

| 属性 | 值 | 后果 |
|---|---|---|
| `isAuthenticated()` | **恒为 `true`** | `!auth.isAuthenticated()` 这道门失效 |
| `getPrincipal()` | 字符串 `"anonymousUser"` | `principal != null` 这道门也失效 |

于是匿名请求被当成"已登录用户 `anonymousUser`"一路走到业务参数校验。

附带问题：限流 key 取的正是这个 userId —— **所有匿名请求共用同一个限流桶**（5 次/小时），一旦有心人打满，后续匿名请求全部 429。

> 项目里其实早有同类教训：`SecurityConfig:85-88` 的 P2-07 注释写着「此前落在 permitAll 内，匿名请求经 `AnonymousAuthenticationToken` 也返回 200 假身份」，`/api/auth/me` 就因此改成了 `.authenticated()`。**新接口重复踩了同一个坑**。

### 3.3 修复（两处）

1. `SecurityConfig`：`.requestMatchers("/api/auth/change-password").authenticated()`，**必须放在 `/api/auth/**` 的 `permitAll()` 之前**（顺序错等于没加）。
2. `AuthController`：纵深防御——显式拒绝 `AnonymousAuthenticationToken`，并要求 principal 是**数字**（JWT 的 subject 恒为数据库自增 id）。

### 3.4 为什么单测是绿的（关键认知）

`@WebMvcTest` 切片排除了 `SecurityAutoConfiguration` / `SecurityFilterAutoConfiguration`，**不会产生匿名令牌**。所以：

- 切片里「未认证 → 503」✅ 绿
- 线上「未认证 → 400」❌ 错

**这是"测试环境与生产环境不一致"的典型形态**：不是断言写错了，而是**被测环境少了生产里必然存在的一个组件**。

### 3.5 补的防护与变异验证

新增 2 条用例，直接用 `AnonymousAuthenticationToken` 构造登录态：

| 用例 | 断言 | 变异后（改回旧逻辑） |
|---|---|---|
| `change_anonymousToken_returns503` | 503（新密码故意设成 `"x"`，若回归会拿到 400，复现线上症状） | **变红**：expected 503, was 200 |
| `change_nonNumericPrincipal_returns503` | 503 | **变红**：expected 503, was 200 |

变异结果：**恰好这 2 条失败，其余 15 条全绿** —— 证明这两条断言有真实保护力，而不是"顺手写个绿的"。

## 四、本批新增发现（未修，记入清单）

### P3 · `JwtAuthFilter` 会用 null principal 覆盖已建立的认证

`security/JwtAuthFilter.java:56-71`：当 `jwtUtil.isValid(token)` 为真、但 `extractUserId(token)` 返回 null 时，仍会构造 `new UsernamePasswordAuthenticationToken(null, null, authorities)` 并 `setAuthentication`。

后果：任何下游 `auth.getPrincipal().toString()` 直接 NPE / 被包成 503。生产中 `isValid` 与 `extractUserId` 同源，正常不会出现；但这是**测试里真实踩到**的路径（本批第 5 条用例最初报 503 就是这个原因）。

建议修法：`if (userId == null) { filterChain.doFilter(...); return; }` —— 与已有的 `isRevoked` / `isBanned` 早退保持一致。

## 四、G3 / G1① 为什么推迟

两者都不是「补个接口」能解决的，需要先做设计决策：

- **G3 待办闭环**：`TodoService.today()` 是**读取时聚合**（待跟进投递 / 近期日程 / 临近截止 / 待投递 四组派生数据），item 的 `id` 只在**组内唯一**（`(group, id)` 才是身份）。要支持「完成 / 忽略 / 延后」，必须新增持久化表（或用户偏好 JSON），并处理「忽略后何时复活」。这是**数据模型决策**，不适合顺手做。
- **G1① 站内提醒**：`TodoPanel` 已经挂在首页。真正缺的不是「首页没有待办」，而是「在别的页面看不到」+「关掉浏览器后彻底收不到」。前者靠导航红点可解，后者需要 PWA 通知（仅在应用打开时有效）或推送服务（要 VAPID + 后端）。**先要你确认值不值得为「关掉浏览器也能收到」引入推送基础设施**。
