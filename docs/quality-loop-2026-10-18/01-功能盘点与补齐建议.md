# 功能盘点与「可添加 / 可完善」建议

> 产出时间：2026-10-18
> 评估对象：`interview-guide` v1.66.20
> **取证口径**：全部结论来自**接口定义与前端调用点的双向对照**（后端 18 个 Controller / 96 个端点；前端 21 个 view / 96 条 `/api/*` 调用）。凡未验证的，明确标注「待阶段三/四验证」。
> **未做的事**：本文件不含 UI 观感与真实操作体感结论——那属于阶段三、四。

---

## 一、功能全貌（8 个域）

| 域 | 页面 | 端点 | 成熟度 | 判断依据 |
|---|---|---|---|---|
| 账号与身份 | Login / Profile / Admin | 14 | ⚠️ 缺恢复能力 | `AuthController` 仅 register/login/logout/me；`MeController` 管导出/导入/AI Key |
| 简历与岗位分析 | Resume / ResumeHistory / JobAnalysis | 16 | ✅ 稳定 | 分析→优化→历史→URL 导入闭环完整 |
| 面试演练 | Interview / History | 12 | ✅ 稳定 | 出题/评估/追问/图片上传/SSE 全链路 |
| 知识库与学习 | Knowledge / Learning / WrongBook | 11 | ⚠️ 只进不出 | 导入 4 个入口，**零删除** |
| 求职进度管理 | Jobs / Favorites / Application / Calendar / Progress | 25 | ✅ 稳定（**但提醒不响**） | 岗位聚合、收藏、投递台账、日历、统计齐全 |
| 职业资产 | Career / Progress（故事库） | 8 | ⚠️ 不可编辑 | 挖掘/计划/故事提取/校验/追问齐全，**缺 PUT** |
| AI 助手 | Agent | 4 | ✅ 稳定 | SSE 流式 + 多会话 + 会话删除 |
| 运营后台 | Admin | 10 | ✅ 稳定 | 概览/源管理/岗位上下架/用户封禁/指标 |

## 二、可完善（把已有功能的最后一公里接上）

> 排序依据：**用户实际受损程度 × 实现成本**。这 7 项的共同特征是——**功能已经建好了 80%，但最后一步没接**。

### G1 🔴 提醒是「死数据」：日历/待办齐全，但系统永远不会主动叫你

| 项 | 内容 |
|---|---|
| **证据** | ① `InterviewEventController` 提供日历事件完整 CRUD（截止/面试）；② `TodoController` 提供「今日待办」；③ 前端全库检索 `Notification / requestPermission / pushManager / showNotification` → **0 命中**；④ 后端检索 `JavaMailSender / smtp` → **0 命中**；⑤ 全后端只有 3 个 `@Scheduled`（向量落盘、注册限流计数清理、岗位刷新），**没有任何"临近提醒"调度** |
| **用户影响** | 用户填了「10-25 投递截止」「10-20 14:00 面试」，这东西只在**他主动打开应用**时才可见。而求职者恰恰是最容易忘事的人群。**这是本产品当前最大的功能断层** |
| **建议** | 三级递进：①**站内提醒**（进入应用即弹出「今日 2 个待办 / 1 个面试」）—— 零网络成本；②**PWA 本地通知**（`sw.js` 已存在，只需申请 `Notification` 权限 + 前端定时比对本地事件）；③**邮件**（需新增 SMTP 通道，成本最高，免费额度受限） |
| **工作量** | ①0.5 人日 ②1 人日 ③2 人日 |
| **优先级** | **P0**（①必须做，②建议做） |

### G2 🟠 只增不删：简历 / 面试会话 / 知识库都没有删除接口

| 项 | 内容 |
|---|---|
| **证据** | 全后端仅 6 个 Controller 含 `@DeleteMapping`（Admin、Agent、InterviewEvent、JobApplication、Me、StoryBank）。`ResumeController`（analyze/upload/history/{id}/optimize/import-url）、`InterviewSessionController`、`KnowledgeController` **均无删除** |
| **用户影响** | 简历分析了几十份、面试练了几十场之后，列表无法清理，只能靠"最新在前"硬扛。知识库导入错的条目**永久残留并继续被 RAG 检索到**——这是质量问题，不只是洁癖 |
| **建议** | 补 `DELETE /api/resume/{id}`、`DELETE /api/session/{id}`、`DELETE /api/knowledge/{id}`；**删除必须校验归属**（防越权），并对知识库删除同步向量库 `doDelete` |
| **工作量** | 1 人日（含越权测试与向量库同步） |
| **优先级** | **P1** |

### G3 🟠 待办只读：能看到，但无法"完成"

| 项 | 内容 |
|---|---|
| **证据** | `TodoController.java` 全文只有 `@GetMapping("/today")`，**无任何 Post/Put/Delete 映射** |
| **用户影响** | 今日待办列出「跟进某公司」「补一份简历」，用户点不掉、勾不上。下次打开还在，久了就无视它 —— 待办面板的可信度归零 |
| **建议** | 补 `PATCH /api/todo/{id}`（status: DONE / SNOOZE / DISMISS）；若待办是**派生**而非持久实体，则改为前端按「已读时间戳」过滤 |
| **工作量** | 0.5 人日 |
| **优先级** | **P1** |

### G4 🟡 故事库不可编辑

| 项 | 内容 |
|---|---|
| **证据** | `StoryBankController` 有 GET / POST / POST `/extract` / POST `/{id}/check` / POST `/{id}/followup` / DELETE `/{id}`，**无 PUT / PATCH** |
| **用户影响** | STAR 故事写完发现措辞不好，只能删掉重建 —— 连带丢失已有的 `check`（校验）与 `followup`（追问）结果，而这两项恰恰是打磨故事的依据 |
| **建议** | 补 `PUT /api/story-bank/{id}`，保留 check/followup 历史；或加「版本」概念 |
| **工作量** | 0.3 人日 |
| **优先级** | P2 |

### G5 🟠 账号不可恢复：无改密、无找回、无邮箱验证

| 项 | 内容 |
|---|---|
| **证据** | `AuthController` 仅 4 个端点（register / login / logout / me）；全后端检索 `reset / forgot / changePassword` 映射 → **0 命中**；无邮件通道 |
| **用户影响** | ①忘记密码 = 账号报废（对**有投递台账、面试记录**的用户是灾难级）；②无法主动改密；③注册不验证邮箱，任意邮箱可占（也侧面解释了「注册限流 5 次/小时」的存在） |
| **建议** | ①`POST /api/auth/change-password`（凭旧密码）0.5 人日；②找回密码依赖邮件通道，与 G1 ③ 共用基建，2 人日 |
| **优先级** | **P1**（改密先行） |

### G6 🟡 岗位详情接口做了，但前端没用

| 项 | 内容 |
|---|---|
| **证据** | `JobAgentController` 有 `GET /api/jobs/{id}`；前端 `JobsView.vue:657` 的 `showDetail(job)` 实现是 `detail.value = job` —— **直接把列表项赋过去，不发请求**；全站无 `/api/jobs/${id}` 调用 |
| **用户影响** | 详情弹窗能显示什么，完全取决于**列表接口返回了什么**。若列表为了性能裁剪了 JD 全文/公司信息，详情就只能显示残缺内容。**待阶段三用真实数据验证**：找一个 JD 很长的岗位，看详情是否被截断 |
| **建议** | 详情弹窗改为按 id 拉取（顺便让该接口产生价值）；或在列表响应里明确「已含全字段」并在注释里锁死，避免后人裁剪 |
| **工作量** | 0.3 人日 |
| **优先级** | P2 |

### G7 🟡 两个接口没有 UI 入口（疑似历史遗留）

| 项 | 内容 |
|---|---|
| **证据** | `GET /api/knowledge/search` 与 `GET /api/knowledge/recent-questions` 在前端 **0 命中**（前端只用 `/ask` 与 `/question-summary`） |
| **判断** | `/search` 是**纯检索不打 LLM**的路径。若保留，它是「零 AI 成本」的知识查询能力，但用户摸不到；若废弃，应删除以免误以为有该功能 |
| **建议** | 二选一：接到 KnowledgeView 的「快速检索」；或标注 `@Deprecated` 并计划下线 |
| **优先级** | P3 |

### G8 🟡 测试套件混入真实联网探针（占 63% 时长）

| 项 | 内容 |
|---|---|
| **证据** | 全量 5 分 07 秒中，7 个 Probe 类合计 **194 秒（63%）**：`FetcherProbeTest` 45.56s、`AtsApiProbeTest` 39.14s、`SourceHealthProbeTest` 30.02s、`tmp/LiveProbeTest` 18.00s、`AtsE2eProbeTest` 17.15s、`tmp/LiveProbe2Test` 14.64s 等；日志里可见真实抓取的 RemoteOK / HN 响应正文 |
| **风险** | ①断网或被墙 → CI 假红；②上游改版 → CI 假红，与本次改动无关；③`src/test/.../tmp/` 下 3 个探针本质是**一次性调试脚本**，不该进测试套件 |
| **建议** | 给探针类打 `@Tag("probe")`，surefire 默认 `<excludedGroups>probe</excludedGroups>`；`tmp/` 三个类直接移出 `src/test`（或删除） |
| **工作量** | 0.5 人日 |
| **优先级** | P2（**建议在阶段二第一批做**，因为它让后续每次回归都快 3 分钟） |

## 三、可添加（新能力）

> 只列**能吃现有数据/基建**的，不列「从零造」的。每项给出价值与成本，**不给百分比承诺**（无基线不做承诺）。

### N1 简历版本对比 ⭐ 推荐

- **吃现成数据**：`/api/resume/history` + `/{id}` 已存每次分析的四维评分与建议
- **用户价值**：改完简历再分析一次，用户最想知道的是「**比上次好在哪、差在哪**」。目前只能自己翻两条历史肉眼比
- **形态**：选两份历史 → 四维雷达叠加 + 建议 diff + 「新增/消失的问题」
- **成本**：1.5 人日（后端只加聚合接口，无新表）｜**优先级 P1**

### N2 求职漏斗分析 ⭐ 推荐

- **吃现成数据**：`/api/application/{list,board,timeline}` 已有 draft → confirm → status 全链路状态
- **用户价值**：回答「我投了 40 家为什么没面试」——投递数 / 回复率 / 面试转化率 / 各渠道有效率。这是求职者最痛的问题，而数据**已经在库里**
- **成本**：1 人日（纯聚合 + 一个图表页）｜**优先级 P1**

### N3 语音作答与表达指标

- **吃现成能力**：`/api/interview/upload-image` 证明多模态入口已通；面试页已有录音权限场景
- **用户价值**：真实面试是**说**出来的。语速、口头禅、停顿、有效信息密度，是文字作答永远测不出的
- **成本**：3–4 人日（ASR 选型 + 音频上传 + 指标计算），且 ASR 有成本/额度约束｜**优先级 P2**

### N4 每周成长报告

- **吃现成数据**：`/api/stats/dashboard` + `/trend`
- **用户价值**：把「练习了 12 次、均分从 68→74」组织成一份可回看的周报，强化留存
- **成本**：1 人日（复用已有的报告导出管线）｜**优先级 P2**

### N5 双人对练 / 邀请点评

- **用户价值**：模拟面试最大的缺口是「没有真人反馈」
- **成本**：5+ 人日（邀请码、房间、消息同步、权限），且与当前「单机工具」定位冲突｜**优先级 P3（本轮不做）**

## 四、建议的推进顺序（三批）

| 批次 | 内容 | 理由 |
|---|---|---|
| **第一批**（随阶段二一起修） | G8 测试治理 → G3 待办闭环 → G5 改密 → G1① 站内提醒 | 全是「小改动、大感知」，且 G8 先做能让后续每次回归快 3 分钟 |
| **第二批** | G2 删除能力 → N1 简历对比 → N2 漏斗分析 | 数据治理 + 两个高价值分析页，共用已有数据 |
| **第三批** | G1② PWA 通知 → G4 故事库编辑 → N4 周报 → N3 语音 | 依赖更多设计决策与外部服务 |

> ⚠️ **边界声明**：以上是**静态审查**结论。阶段三（96 个页面场景）与阶段四（3 条真实链路）可能推翻其中部分判断——尤其是 G1 的严重程度与 N1/N2 的真实需求强度，**必须用真机走查校验后再定稿**。届时本文件会更新，不另行新建。
