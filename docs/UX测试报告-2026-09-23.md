### 4.2 出题质量评估

- **相关性**：5 道题全部围绕所填 JD 的「高并发 / JVM 调优 / MySQL / 消息队列」关键词，无泛泛而谈的通识题。
- **标签合理性**：分类为「项目深挖」3 题 +「核心技能」2 题；难度为 MEDIUM 4 题 + EASY 1 题，与所选「打基础」档位一致。
- **题干质量**：第 1 题「你提到有高并发经验，请结合实际项目说明你们是如何设计缓存架构的？比如遇到过哪些典型的缓存问题（如缓存穿透、击穿、雪崩），你们是怎么解决的？」——既接住了简历线索，又给出了追问方向，具备真实面试官的提问质感。第 3 题「假设你负责的系统在生产环境突发 OOM，你会如何快速定位问题？」属典型的场景化深挖题。

### 4.3 评分准确性

| 检验项 | 方法 | 结论 |
|---|---|---|
| 答非所问识别 | 故意用「缓存架构」答案回答「Spring Boot 自动装配」题 | **准确**——判 25 分并明确指出「面试前应仔细审题，确认问题后再作答；遇到听不懂的问题可主动澄清，而非强行回答其他话题」 |

| 评语文案稳定性 | 同上，比对 strengths 字段 | **不一致**——分数稳定但文字表述每次都不同（不影响理解，仅说明模型非确定性） |

### 4.5 简历上传、解析与 AI 输出一致性对照

| 用例 | 结果 |
|---|---|
| 上传 .txt（multipart/form-data） | **200 / 1.21s**——返回 `resumeText`（844 字，解析正确）+ `analysis`（1041 字，4 维度评分） |
| 上传 .docx | **正确拒绝**——code=400「仅支持 PDF / HTML / MD / TXT 格式的简历文件（Word 请转换为 PDF）」 |
| analyze 传空白文本 | **正确拒绝**——code=400「简历内容不能为空」 |
| **相同文本重复提交** | **输出逐字节一致**——首次 15.35s，重复 1.23s，**加速 12.5x**（Redis 缓存命中） |
| **微改文本（仅追加一段经历）** | **输出不同且耗时 66.76s**——综合分 85 → 88，维度 85→88 / 85→87，漂移 +3 |

**一致性结论与风险**：「同一份简历分析结果一致」这一体验**来自缓存而非 AI 的确定性**。缓存命中时输出逐字节相同；一旦缓存过期或文本有一字之差，就会重新生成并产生分数漂移（本次仅追加一段经历即 +3 分）。这意味着「同一份简历两次分析分数不一样」是可预期的用户可见现象。建议：① 在结果区标注「结果已缓存，内容未变更时不会重新分析」；② 不要在文案上承诺分数的可复现性；③ 若业务需要稳定的纵向对比，应把分数快照落库并标注生成时间，而不是依赖实时重算。另需注意简历分析同样存在长尾：15.35s vs 66.76s，波动 4.3x。

### P0-01　[P0] 面试题持久化 100% 失败，且前端静默降级、用户无感

- **问题类型**：功能缺陷（核心链路）
- **涉及位置**：`POST /api/session/{sessionId}/questions ｜ frontend/src/views/InterviewView.vue:771-781`
- **复现步骤**：
  1. 普通用户登录 → 「模拟面试」→ 填目标岗位 → 点「开始面试」
  2. 前端调用 POST /api/interview/questions 生成题目（AI 返回的每题含 keyPoints: string[]）
  3. 前端把解析后的题目数组原样 POST 到 /api/session/{id}/questions
- **预期行为**：题目落库并返回带 id 的题目数组，后续答题通过 questionId 关联；历史回顾可回看题目与回答
- **实际行为**：接口返回 HTTP 200 + body.code=400「请求体格式错误，请检查 JSON 语法」；前端 catch 仅 console.warn('题目持久化失败，历史回顾将不可用')，流程照常继续，用户完全无感
- **证据**：
  - 实测 A：body 含 keyPoints 数组 → {"code":400,"message":"请求体格式错误，请检查 JSON 语法"}
  - 实测 B：同一题目去掉 keyPoints → {"code":200,"message":"success","data":[{"id":2,...}]}
  - 实测 C：keyPoints 传字符串 → 200 success；实测 D：keyPoints=null → 200 success
  - 根因：后端签名为 @RequestBody List<Map<String, String>>（InterviewSessionController.java:115），Jackson 无法把 JSON 数组反序列化成 String
- **根因分析**：AI 出题提示词要求返回 keyPoints 数组，后端持久化接口却声明为 Map<String,String>，两侧契约不一致；且该失败被前端 catch 吞掉，不阻断主流程，形成静默降级
- **解决方案**：
  - 【推荐·前端止血】InterviewView 提交前做字段白名单映射，只发送 question/category/difficulty/referenceAnswer 四个字段（Question 接口定义本来就只有这四个），5 行代码即可恢复持久化，且不改后端契约
  - 【后端加固】saveQuestions 入参改为 List<Map<String, Object>> 或独立 DTO + @JsonIgnoreProperties(ignoreUnknown=true)，并显式忽略未知字段，避免同类字段演进再次打穿
  - 【测试门禁】补一条集成测试，直接使用真实 AI 输出的题目 JSON（含 keyPoints 数组）作为请求体，断言 200
  - 【可观测性】持久化失败时给用户一条可见提示（如「本次题目未能保存到历史，刷新后可能丢失」），不要只 console.warn
- **影响面**：历史面试记录永远为空；答题记录无 questionId 关联 → 错题本、成长趋势、题目汇总、收藏全部拿不到数据；核心闭环「出题→答题→复盘」实际断裂

### P1-02　[P1] 登录失败锁定与注册限流在生产环境失效（按 IP 的限流键不稳定）

- **问题类型**：安全 / 可靠性
- **涉及位置**：`AuthController（login/register）｜ util/ClientIpUtil.java`
- **复现步骤**：
  1. 连续 4 次用错误密码登录同一账号，观察返回文案中的「还可尝试 N 次」
  2. 连续 9 次调用 POST /api/auth/register（配置为 5 次/小时/IP）
  3. 对照实验：连续调用 POST /api/jobs/refresh（按 userId 限流，1 次/5 分钟）
- **预期行为**：失败次数应依次递减 4→3→2→1 并在第 5 次锁定 5 分钟；第 6 次注册应返回 429
- **实际行为**：登录剩余次数呈 4→3→4→3 交替；注册连续 9 次全部 200 success（id 70~75 均创建成功），从未出现 429
- **证据**：

  - 显式声明受信代理网段（新增环境变量如 APP_TRUSTED_PROXY_CIDRS，按 Render 实际出口网段配置），使 XFF 解析路径生效
  - 或在网关层强制注入并覆盖 X-Forwarded-For，后端只信任该头的最右值
  - 对注册/登录增加「按 username」维度的限流作为兜底（即使 IP 键不稳定也能拦住针对单账号的暴力破解与批量注册）
  - 在 /api/health/detail 暴露当前解析出的限流键样例（脱敏哈希），使此类失效无需翻日志即可自诊断
- **影响面**：暴力破解防护形同虚设（实际可尝试次数约翻倍且永不锁定）；注册接口可被脚本无限批量注册垃圾账号

### P1-17　[P1] AI 评分返回破损 JSON 时前端静默丢分，评分面板只显示「-」

- **问题类型**：功能缺陷（AI 输出契约）
- **涉及位置**：`POST /api/interview/evaluate ｜ InterviewService.java:233-275 ｜ InterviewView.vue:922（safeParse → v-if="evalResult"）`
- **复现步骤**：

  4. （复现率测定）对同一段回答连续提交 6 次，统计返回体不可解析的次数
- **预期行为**：返回可解析的 JSON，四个维度显示分数并给出改进建议；若 AI 输出异常，应返回明确失败提示并提供重试入口
- **实际行为**：约 1/3 的调用返回 HTTP 200 + body.code=200，但 data 字符串 JSON.parse 失败，例如真实样本中出现 「"回答在中途截断:"再用Con"后内容完全丢失，未说完"」——字符串值内部混入未转义 ASCII 双引号。前端 safeParse(data,{}) 退化为 {}，而 v-if="evalResult" 对 {} 判定为真，于是面板照常渲染但四个维度全部显示「-」、改进建议列表为空、且没有任何错误提示
- **证据**：
  - 复现率 A：同一 payload（200 字回答）连续 6 次评分，失败 2 次 → 33%
  - 复现率 B：另一组 6 次（含 200/600/1200/2500/5000/8000 字不同长度），失败 2 次 → 与长度无关
  - 失败样本原文与解析异常信息留存于 score_repeat_result.json / score_len_result.json
  - 浏览器渲染复现：以真实失败样本经请求拦截注入后，面板显示「AI 评估结果 - 综合 - 完整性 - 准确性 - 表达力」，四个「-」（图 18）
  - 代码路径：InterviewView.vue:922 `safeParse<EvalResult>(data, {})` → 171 行 `v-if="evalResult"` → 182/189/196/203 行 `?? '-'`
- **根因分析**：评分提示词存在两条互相冲突的规则：规则 4 要求表达力维度「有则如实扣分并指出原句」（诱导模型引用用户原文），规则 3 又要求「不要在字符串值中使用引号」。模型为「指出原句」而使用 ASCII 双引号包裹用户原文，直接击穿 JSON 结构。JsonRepairUtil 未能修复该形态，且接口仍以 200 + code=200 把脏数据下发，把「AI 输出不合规」伪装成「成功」
- **解决方案**：
  - 【后端·止血】评分返回前做一次 JSON 解析校验，解析失败直接返回 `Result.error(502, "AI 评分结果格式异常，请重试")`，绝不把脏数据当成功下发
  - 【后端·根治】把评分 JSON 的解析与结构化搬到后端完成（Spring AI 的 `.entity()` / BeanOutputConverter），前端只消费结构化字段，彻底消除前端解析失败的可能
  - 【提示词】消解规则冲突：统一为「引用用户原句时一律用《》，任何情况下禁止出现 ASCII 双引号」，并把该约束提到输出要求的首条、附上正反例
  - 【前端】safeParse 拿到 fallback 时应判定为失败：当 `overallScore` 既不是数字也不为 0 时，显示「评分结果解析失败，点击重试」而不是渲染空面板
  - 【可观测性】对 `interview-evaluate` 的 JSON 修复失败率打点，超过阈值告警——这类问题当前在监控里完全不可见
- **影响面**：约 1/3 概率用户提交回答后拿不到任何评分，且没有提示；该题也不会进入复盘报告的 sessionEvals，导致报告的总分与题数被静默拉低，用户既看不到失败也无法察觉数据缺失

### P1-25　[P1] 作答附图（多模态）上传 100% 失败，且健康检查不覆盖存储、占位符告警失效、真实错误被吞

- **涉及位置**：`POST /api/interview/upload-image ｜ SupabaseStorageService.java:43-64（warnIfPlaceholder）/ :70-100（upload）｜ application.yml:205-208`

- **证据**：

  - 校验分支全部正确：text/plain → 「仅支持图片文件（jpg/png/webp/gif）」；SVG → 同上；伪装 PNG → 「文件内容与图片格式不符，已拒绝」；6MB → 「图片大小不能超过 5MB」
  - SSRF 防护有效：外部域名 → 「域名无法解析，请检查 URL」；内网元数据地址 → 「不支持访问内部地址」
  - `GET /api/health/detail` → `{"status":"UP","database":{"status":"UP"},"redis":{"status":"UP"},"rag":{…"DEGRADED"},"degraded":["rag"]}`——无 storage 项
  - `GET /actuator` 仅暴露 health / info（无 env / configprops，未泄露配置，安全姿势正确）
  - 代码级：`warnIfPlaceholder()` 检测的是 `placeholder.supabase.co` / 以 `placeholder` 开头的 key，而 application.yml 的默认值是 `https://your-project.supabase.co` / `your-service-key` → <b>该告警永远不会触发</b>，恰好落在它注释里想防的「上传功能静默失效、没人知道为什么」
  - 代码级：`upload()` 中 `safeName = fileName.replaceAll("[^a-zA-Z0-9._-]", "_")` 会把调用方传入的 `interview/<uid>/<ts>.png` 里的 `/` 全部替换为 `_`，目录结构被拍平（命名约定两侧不一致）
  - 代码级：`restTemplate.exchange` 默认在 4xx/5xx 直接抛异常，因此紧随其后的 `if (!response.getStatusCode().is2xxSuccessful())` 是死代码，Supabase 返回的真实错误（如 401 InvalidJWT / 404 Bucket not found）被吞掉
- **根因分析**：`upload()` 走 `restTemplate.exchange` 调 Supabase Storage REST API，异常被控制器统一 catch 成笼统的 500；由于 RestTemplate 默认对 4xx/5xx 抛异常，代码里那段本应记录 `status + body` 的判断永远执行不到，于是真实原因（凭据无效 / bucket 不存在 / URL 为占位符 / 网络不可达）全部丢失。同时健康检查未纳入 storage，占位符告警的字符串又与配置文件默认值不匹配——三重失明叠加，使一个「100% 失败」的核心功能在监控与告警层面完全静默
- **解决方案**：
  - 【先定位】让 RestTemplate 使用不抛异常的 errorHandler（或捕获 HttpClientErrorException），把 Supabase 返回的 status 与 body 写入日志，并纳入 /api/health/detail —— 否则无法知道是 401、404 还是 DNS 失败
  - 【再修复】按真实错误处理：核对生产环境 SUPABASE_URL / SUPABASE_SERVICE_KEY / SUPABASE_BUCKET 是否已注入，bucket 是否存在、是否允许 service key 写入（Supabase 免费项目长期闲置会被暂停，需确认项目状态）
  - 【可观测性】把 storage 纳入健康检查：启动时与每 N 分钟做一次轻量探测（如 GET bucket 元信息），失败则把 `storage` 加入 `degraded` 数组，让故障在监控里可见
  - 【修占位符检测】`warnIfPlaceholder()` 改为与 application.yml 默认值一致（检测 `your-project.supabase.co` / `your-service-key`），或更稳妥地在配置缺失时直接 fail-fast
  - 【修文件名清洗】`safeName` 保留 `/`（或在调用方传入前完成清洗），避免 `interview/<uid>/` 目录被拍平成文件名前缀
  - 【降级体验】上传失败时前端应给出可操作提示（如「附图上传失败，可不附图继续作答」），而不是让用户反复重试一个必然失败的按钮

### P2-24　[P2] AI 已生成并持久化了参考答案，但评分时未传入，提示词「结合参考答案逐项核对」形同虚设

### P2-04　[P2] 搜索被网关 WAF 拦截时，前端误报「后端冷启动」并静默重放一次请求

- **问题类型**：易用性 / 错误提示误导
- **涉及位置**：`frontend/src/api/index.ts（isColdStartError + 冷启动重放）｜ 招聘广场搜索框`
- **复现步骤**：
  1. 登录后进入「招聘广场」
  2. 在搜索框输入 ' OR 1=1 并回车（实测普通关键词 Java 正常）
- **预期行为**：要么正常返回结果，要么明确提示「该搜索词包含被安全策略拦截的字符，请修改后重试」
- **实际行为**：请求被 Render 边缘以 403 + HTML 拦截页拒绝；浏览器因响应缺少 CORS 头判定为网络错误（net::ERR_FAILED）；前端将其识别为「后端冷启动」→ 自动重放一次（日志可见 REQ/FAIL 两轮）→ 最终提示「后端服务唤醒超时，请稍后重试（免费实例冷启动约需 1-2 分钟）」；列表无任何结果变化
- **证据**：
  - 浏览器网络日志：REQ jobs?keyword='+OR+1=1 → CONSOLE-error Access to XMLHttpRequest ... blocked by CORS policy → FAIL net::ERR_FAILED → REQ（重放）→ FAIL
  - 接口层对照：curl 同一 URL 返回 HTTP 403 + <title>Blocked</title> 的 HTML 拦截页；' OR 1=1 可稳定复现，而 1' or '1'='1、union select 1,2、<script>alert(1)</script> 均不被拦截
  - 普通关键词 jobs?keyword=Java 返回 200 且结果正常，说明搜索链路本身可用
- **根因分析**：安全网关在应用之外，其 403 响应不含 CORS 头 → 浏览器只能上报为网络错误；前端的冷启动判定把所有「无响应体 + 网络失败」都归因为后端未就绪，因而给出完全误导的文案，并触发对 GET 的自动重放
- **解决方案**：
  - 前端区分错误来源：HTTP 403 且响应体非业务 JSON（HTML）时，提示「该搜索词被安全策略拦截，请更换关键词」，不要走冷启动文案
  - 服务端对 keyword 做字符白名单与长度校验（如仅允许中英文/数字/常见符号，≤50 字），从源头避免请求打到 WAF
  - 自动重放策略收紧：仅在「明确的后端未就绪信号」（ECONNABORTED/502/503/504 且非业务 JSON）时重放，网络层失败不重放
- **影响面**：用户看到与事实完全不符的「后端正在冷启动」，会误以为服务故障并反复等待；同时每次搜索浪费一次重放请求

### P2-05　[P2] axios 拦截器把 HTTP 403 一律当作「认证失效」，会清 token 强制跳登录

- **涉及位置**：`frontend/src/api/index.ts:218-225`
- **复现步骤**：
  1. 静态阅读：if (error.response?.status === 401 || error.response?.status === 403) { clearAuth(); window.location.href = '/login?redirect=...' }
  2. 触发条件：任一接口返回带 CORS 头的 403（网关策略调整、启用同源反向代理、或后端权限 403 直连同源路径）

  - 本次测试中该分支未被触发：WAF 的 403 因缺少 CORS 头被浏览器判定为网络错误，未进入 axios 的 403 分支（因此本项为静态分析结论，未做破坏性实测）

  - 仅 401 触发 clearAuth + 跳登录；403 走业务错误提示并停留在当前页
  - 若担心历史兼容，可保留 403 的兜底判断但加条件：仅当响应体缺失或为非业务 JSON 时才视为认证失效
  - 补一条单测覆盖「403 不清 token」
- **影响面**：潜在的用户被静默登出（丢失当前操作上下文）且看不到任何权限解释，属埋点式体验事故

### P2-19　[P2] 复盘报告的「综合分」与三个维度加权结果不自洽，实测最大偏差 +33.8 分且方向不稳定

- **证据**：

  - 逐题实测：Q2（25 / 20 / 15 / 30）→ 加权 21；Q3（30 / 20 / 15 / 50）→ 加权 27；Q4（25 / 0 / 15 / 50）→ 加权 21

  - 【提示词】明确写出「overallScore 必须严格等于三维加权结果（四舍五入取整），不得独立判断」，并在示例中给出对应数值

### P3-13　[P3] DELETE 非幂等；畸形请求返回 500 且文案泄露内部语义

- **问题类型**：接口健壮性
- **涉及位置**：`DELETE /api/calendar/event/{id} ｜ 全局异常处理 ｜ 字段长度校验`
- **复现步骤**：
  1. 创建日程后连续两次 DELETE 同一 id
  2. POST /api/calendar/event，body 为非法 JSON（{not json）
  3. POST /api/calendar/event，title 传 20 万字符
- **预期行为**：DELETE 幂等（重复删除返回成功或 404 语义稳定）；非法 JSON → 400「请求体格式错误」；超长字段 → 400「标题过长（≤200 字）」
- **实际行为**：第二次 DELETE → 400「请求参数错误：日程不存在：1」；非法 JSON → HTTP 500 +「服务器内部错误」；20 万字符 title → HTTP 500 +「数据库操作失败，请联系管理员」
- **证据**：
  - DELETE /api/calendar/event/1 → 200 success；再次 DELETE 同一 id → 400 日程不存在

- **影响面**：用户遇到 500 会认为是系统故障；「数据库操作失败」泄露实现细节；DELETE 非幂等会给重试/并发场景带来不必要的报错

### P2-26　[P2] 从历史会话继续面试后结束，复盘报告只统计「本次页面内」的作答，丢弃该会话既有得分记录

- **问题类型**：数据不一致 / 报告失真
- **涉及位置**：`InterviewView.vue（resumeSession / sessionEvals / finishSession / answeredCount）`
- **复现步骤**：
  1. 打开「面试历史」，选一场已有多题作答记录的会话（本场 4 题，其中 2 题已有 35 分、28 分的评分记录）
  2. 从历史记录恢复该会话进入答题
  3. 用「跳过本题」推进到最后一题，只作答这一题（避免额外 AI 消耗）
  4. 点击「结束面试」，查看复盘报告的抬头与「逐题得分」区块
- **预期行为**：复盘报告应覆盖该会话的全部已作答题目（含此前各题的既有得分），与「面试历史」页面数据一致
- **实际行为**：报告抬头写「基于本次 1 道作答的结构化总结」，「逐题得分」只有 1 条；而该会话在服务端实际存有 4 题、其中 2 题早已有评分记录（35 分 / 28 分）。用户从「继续面试」这条路走完，拿到的是一份「丢题」的报告
- **证据**：
  - 报告截图（图 20）：抬头「基于本次 1 道作答」，「逐题得分」仅 1 条
  - 接口实测：GET /api/session/61fd37c5-…/questions 返回 4 题，id=2 的 evaluationScore=35、id=4 的 evaluationScore=28
  - 代码：sessionEvals 为页面级 ref，仅在 submitAnswer 成功时 push；resumeSession（InterviewView.vue:482-500）只恢复 sessionId / questions / qIndex，不拉取既有评分回填 sessionEvals
- **根因分析**：复盘报告的数据源是纯前端的 sessionEvals，而非服务端该会话的评分记录。正常「新建面试」流程下两者等价，但「继续面试」会破坏这个等价关系：既有题目由 resumeSession 载入、得分只存在于服务端，前端 sessionEvals 从空数组开始，于是报告只反映本次页面内新作答的题目。finishSession 又以 sessionEvals.length 作为 answeredCount 与「是否弹报告」的判据，使缺失被进一步固化到报告抬头文案里
- **解决方案**：
  - 【推荐】resumeSession 拿到题目后，用题目自带的 evaluationScore / userAnswer 回填 sessionEvals，报告中标注「含历史作答 N 题」，避免重复计分
  - 或让复盘报告改为以服务端数据为准：结束面试时请求该会话的评分汇总接口，前端只负责渲染
  - 若坚持页面级统计，至少把抬头文案改为「本次新作答 N 题 · 该会话累计 M 题」，消除「丢题」观感
  - 补一条端到端断言：恢复会话后结束面试，报告的逐题条数应等于该会话已作答题目数
- **影响面**：「继续面试」是历史页的主入口之一，走这条路拿到的复盘报告与历史页数据自相矛盾，用户会认为报告丢了记录；对以复盘为主要价值的面试产品，这直接损害核心产出物可信度

### P2-28　[P2] 语音识别自然结束后按钮卡死：一直显示「语音识别中…」且点击无任何反应

- **问题类型**：功能缺陷 / 状态机未复位
- **涉及位置**：`InterviewView.vue（toggleSpeech / speechRecording）｜ utils/speech.ts:205-208（onend 未回调 UI 复位）｜ components/BaseButton.vue:53`
- **复现步骤**：
  1. 进入答题页，点击「语音作答」并授权麦克风（此时识别正常开始，按钮变为「语音识别中… 再点一下结束」）
  2. 正常说一句话后停顿数秒 —— Chrome 的 Web Speech API 即使在 continuous=true 下，也会在静音一段时间后自行触发 onend 结束识别
  3. 观察按钮状态与右侧指标文案
  4. 再点击一次按钮（UI 上明确写着「再点一下结束」）
- **预期行为**：识别结束后按钮应复位为「语音作答」；再次点击应能重新开始识别
- **实际行为**：onend 触发后：① 按钮仍带加载转圈显示「语音识别中… 再点一下结束」、保留 is-recording 样式；② 再点一次<b>完全没有反应</b>——既不结束也不重新开始，无 toast、无状态变化；③ 唯一的恢复方式是离开页面。讽刺之处在于：只有<b>真的授权了麦克风</b>、即真正想用这个功能的用户才会踩到它
- **证据**：
  - 桩注入实测（图 23）：以符合规范的 onstart→onresult→onend 事件序列驱动后，按钮文本仍为「语音识别中… 再点一下结束」、is-recording=true，而右侧指标已更新为「语速 适中（0 字/分）· 时长 0s」——证明 onend 确实已触发
  - 计数证据：桩内计数器在「自动结束」与「第二次点击」前后均为 {start:1, stop:0, abort:0}，即第二次点击连 recognition.start()/stop() 都没有调用到
  - 代码定位：utils/speech.ts 的 onend 只做 `recording=false` 并回调 onMetrics，**没有把 UI 的 speechRecording 置回 false**；而 components/BaseButton.vue:53 是 `if (props.disabled || props.loading) return` —— loading 为真时点击处理器直接静默 return，且 DOM 上按钮并未 disabled，所以既没有反应也没有报错，用户完全无从判断
  - 对照组（图 22）：真实环境下拒绝麦克风权限时，onerror 分支正确处理——提示「麦克风或语音服务未授权，请授权后重试」且按钮正确回到空闲态。说明缺陷只在 onend 这一条路径上
- **根因分析**：UI 状态 `speechRecording` 与识别器内部状态 `recording` 是两套独立变量，但只有 onstart/onerror 两条路径会同步 UI 状态，**onend 这条最常走的正常结束路径被漏掉了**。叠加 BaseButton 在 loading 时静默 return 的实现，使「状态没复位」升级为「按钮彻底不可用」——两个各自看起来合理的实现细节，组合出了一个用户无法自救的死状态
- **解决方案**：
  - 【最小改动】在 utils/speech.ts 的 onend 回调中增加一个 onEnd 钩子，由 InterviewView 在其中执行 `speechRecording.value = false`
  - 【更稳】把 UI 状态改为从识别器状态派生（如让 createSpeechRecorder 暴露一个响应式 state），避免两套状态各自维护、必然漂移
  - 【防御】BaseButton 在 loading 时不要静默 return，至少给出可见反馈；或对「语音识别中」这类长驻状态不要复用 loading 语义（loading 隐含「短暂等待」，而语音识别是可持续数分钟的会话状态）
  - 【可观测】识别结束/异常时在界面上留下痕迹（如「识别已结束，共 X 字」），避免用户面对一个无反馈的卡死按钮
- **影响面**：语音作答是面试页的辅助输入方式，一旦卡死用户无法自行恢复，只能刷新或离开页面——而刷新会清空当前作答状态。对「用语音代替打字」的用户等于功能失效

### P2-29　[P2] 复盘报告被误点遮罩即关闭，且关闭后没有任何入口可以重新打开

- **问题类型**：交互缺陷 / 不可逆操作无确认
- **涉及位置**：`InterviewView.vue:225（report-mask 的 @click.self）｜ InterviewView.vue:1070-1077（两个关闭函数）`
- **复现步骤**：
  1. 完成一场面试，结束面试后复盘报告弹出
  2. 在报告弹窗外侧的遮罩空白处点击一下（x=12, y=12）
  3. 观察页面状态，并检查界面上是否还有重新打开报告的入口
- **预期行为**：要么点击遮罩不关闭报告（因为报告是面试的核心产出物），要么关闭后仍保留可重新打开的入口；至少在关闭前给出确认
- **实际行为**：点一下遮罩报告立即关闭，页面回到面试准备页；此后页面上可见按钮为「求职工具 / 自适应 / 打基础 / 稳中有升 / 挑战自我 / 开始面试」，<b>没有任何「查看报告 / 复盘」入口</b>，报告无法再打开。而 finishSession 里 resetSession() 已清空 questions 与 sessionId，「结束面试」按钮也随之消失，用户无法通过重走流程找回该报告
- **证据**：
  - 报告关闭后截图（图 24）：页面已回到准备页，按钮清单中无任何报告入口
  - 代码定位：`reportOpen` 在整个文件中<b>只有 finishSession 一处被置为 true</b>（grep 结果唯一），没有任何按钮或路由可以重新触发它
  - 代码注释与实现不符：closeReportGoSetup 上方写着「报告内容仍保留在本次会话内，可再次打开直到离开页面」，但实际不存在任何「再次打开」的入口
  - 对照（图 25）：同一弹窗的「查看历史记录」按钮工作正常（正确跳转 /history），说明弹窗本身的按钮链路无问题，问题只在「关闭即永久丢失」
- **根因分析**：报告弹窗被当作一个普通模态框处理（遮罩点击关闭、无重开入口），但它的语义是「一次面试的最终产出物」而非「临时弹层」。同时 finishSession 在打开报告的同时就调用了 resetSession() 清空会话状态，使「重走流程再看一次」这条兜底路径也被切断
- **解决方案**：
  - 【推荐】遮罩点击不再关闭报告，只保留右上角 ✕ 与底部两个明确按钮关闭
  - 在面试准备页保留一个「查看上一场复盘报告」入口（报告数据已在内存中，无需重新请求）
  - 若坚持遮罩关闭，关闭前用 ElMessageBox 确认，或提供「刚刚的报告」浮层/Toast 快捷入口
  - 修正 closeReportGoSetup 的注释，使其与实际行为一致（当前注释承诺了不存在的功能）
- **影响面**：复盘报告是模拟面试的核心价值产出。一次无意的遮罩点击就会永久失去查看入口，且用户没有任何心理预期（遮罩点击在多数产品里是可恢复的轻操作）；用户若想再看一次，只能重新做一场面试

### P3-30　[P3] 语音表达指标在无有效语音时显示自相矛盾的「语速 适中（0 字/分）」，且精心编写的 feedback 文案从未被展示

- **问题类型**：文案自相矛盾 / 无效代码

- **实际行为**：显示「语速 适中（0 字/分）· 时长 0s」——一边断言语速「适中」，一边给出的数值是 0 字/分、0s，自身即矛盾（图 23）
- **证据**：
  - 截图（图 23）：按钮右侧文案「语速 适中（0 字/分）· 时长 0s」
  - 代码：utils/speech.ts 的 computeSpeechMetrics 已经针对该场景写好文案——`durationSec===0 || n===0` 时 feedback = 「未能识别到有效语音，请确认麦克风权限已开启、环境安静后重试。」

- **影响面**：轻微——不影响功能，但这类「数值与结论打架」的文案会削弱用户对表达分析的信任；且已写好的指引文案被浪费，用户不知道下一步该做什么

| 实测可用性 | `POST /v1/chat/completions`(agnes-2.5-flash) → 200，1.57s；**base_url 必须带 /v1**，否则被网关拦截返回 403 HTML |

### 6.2 智谱 GLM（兜底）

| 项目 | 结论 |
|---|---|
| `glm-4.5-flash`（当前兜底） | 官方公告**已于 2026-01-30 下线**，自动路由至 `glm-4.7-flash`；实测仍返回 200（4.04s），属隐性依赖 |
| `glm-4-flash`（末位保险） | 长期免费，实测 200 / 0.36s，最稳定 |
| `glm-4.7-flash`（现役免费档） | 200K 上下文 / 128K 输出，免费；**实测 429，code 1305「该模型当前访问量过大」** |
| 免费档速率限制 | 官方按「并发请求数」限制，不同模型/权益等级不同，**未公开具体数值**；第三方汇总约 60 RPM / 10 万 TPM / 并发 1-2（仅供参考） |

### 6.3 Embedding（自托管）

- 方案：fastembed(ONNX) + `BAAI/bge-small-zh-v1.5`（512 维），独立部署于 Render 免费实例，模型构建期烘焙进镜像。
- 成本：**API 调用零成本、无 token 额度限制**（相对第三方 embedding 的核心优势）。
- 真实约束：受 Render 免费层约束——**750 instance-hours/月/workspace，超额会暂停全部免费服务**；主后端 7×24 常驻已占约 730h，两服务都常驻必然超额。
- 副作用：空闲被挂起 → 首次请求冷启动，直接表现为**检索 25.7s**；本次还出现向量入库失败导致知识库整体降级。

## 七、免费额度使用策略

1. **额度红线优先**：保活维持北京时间 07:00–01:00、只保活主后端（约 540h/月）。**不要把 embedding 纳入常驻保活**（两服务常驻 ≈1460h/月，必然触发 Render 全站暂停），改为按需唤醒 + 前端进度提示。
2. **把 Agnes 10 RPM 当硬约束**：现网闸门「前台 5 + 后台 2 = 7 并发」稳态可行，但批量出题 + 岗位分类同时触发会撞限流。建议前台许可 ≤5、同用户 AI 操作加 3~5s 最小间隔、429 时指数退避并换链上下一个节点。如需更高额度可评估 Token Plan Starter（约 $4/月，1500 次/5 小时）或完成企业认证提升到 20 RPM。
3. **换掉已下线的模型别名**：兜底节点由 `glm-4.5-flash` 改为官方现役免费档 `glm-4-flash-250414`（128K）或 `glm-4.7-flash`（200K，但当前 429 频繁）；保留 `glm-4-flash` 作为末位保险（实测最快最稳）。
4. **省调用的三处杠杆**：① 复用现有 Redis 缓存（简历分析/优化/出题均已用 `sha256Short` 生成缓存键）；② 知识库自动补充（30 次/小时）在低峰期 01:00–07:00 暂停，把额度留给前台交互；③ 对 (query, topK) 加短 TTL 缓存，避免同一检索重复触发 embedding 冷启动。
5. **用现成接口做监控**：`GET /api/admin/metrics` 的 `aiCalls` 作每日基线；`GET /api/health/detail` 的 `rag.lastFailure` 作 embedding 健康哨兵（本次正是靠它定位到「UUID string too large」）；建议再补一个「今日 AI 调用次数 / 距上次 429 时间」的轻量指标。

6. **堵住第二轮实测发现的三个额度漏斗**：
   - **空回答也消耗一次评分调用**（P3-22）：后端改为 `isBlank()` 校验 + 最短长度 5 字，直接省掉一类无效调用。在 10 RPM 的免费档下，这类调用会成比例挤占真实用户的评分配额。
   - **破损 JSON 的调用是纯浪费**（P1-17）：约 1/3 的评分调用返回不可用结果，用户只能重试 → 等于把额度烧在重试上。修好提示词的规则冲突后，这部分额度可直接回收。
   - **长尾超时同样烧额度**（P2-21）：Q5 超过 71s 才返回，若用户中途刷新，这次调用已消耗但结果被丢弃。建议后端加 60 秒超时，前端提供「重试」而不是让用户「刷新页面」。
   - **把缓存用在刀刃上**：简历分析已实现缓存（实测 12.5x 加速），但**评分接口无缓存**——这与「同一题同一答的评分本身高度稳定（实测 3 次完全一致）」的事实叠加，说明评分完全可以按 `sha256(question + userAnswer)` 做短 TTL 缓存，既省额度又顺带解决了评分一致性问题。
