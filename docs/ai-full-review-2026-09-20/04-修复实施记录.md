## 二、P1 修复明细

### P1-1 招聘多源聚合失效

| 项 | 内容 |
|---|---|
| 问题 | 4 个招聘源共享同一个 `collected` 列表，且每源以 `out.size() >= MAX_PER_SOURCE(8)` 判断中断。首个源填满 8 条后，2–4 号源**首次判断即 break、恒贡献 0 条**，`MAX_TOTAL=12` 永不达到——「多源并行提升命中率」的设计意图完全落空 |
| 修复 | 抽出 `mergeFromSource(out, fromSource, limit)`：**按本源已并入条数**计数；4 个 fetcher 统一改为「先本地解析成 list，再合并」 |
| 文件 | `service/job/WebJobSearcherService.java` |
| 新增测试 | `WebJobSearcherServiceTest` +4：单源上限、**首源填满后第二源仍贡献**、4 源累计 32 条、null/空源 |
| 验证 | 单测断言 `mergeFromSource` 在首源已并入 8 条后，第二源仍能并入 8 条（修复前为 0） |

### P1-2 流式路径缺少空正文判定

| 项 | 内容 |
|---|---|
| 问题 | `call` 路径对「HTTP 200 但正文为空」判失败并继续降级，`stream` 路径**漏做该判定** → 上游「思考模式耗尽 max_tokens」时用户拿到**空白回答且无任何错误提示** |
| 修复 | 重构为 `streamFrom(idx, ...)` 递归降级，两级降级条件统一为 `hasUsableContent`：①订阅抛错；②**流正常结束但无任何可用正文**（经 `filter(hasUsableContent)` + `switchIfEmpty` 捕获）。已发出 token 后仍不降级（保持 v1.23.1 既有语义）。降级链耗尽时保留**最后一个节点的真实异常**，不改变既有诊断行为 |
| 文件 | `ai/FallbackChatModel.java` |
| 新增测试 | `FallbackChatModelTest` +5：空正文降级、纯空白降级、**全链空正文抛 503 业务异常**、空 chunk 被过滤、空正文后降级中途失败仍传播错误 |
| 验证 | 原有 18 项（含「已发出 token 不降级」「全链失败传播原错误」）全部保持通过 |

## 六、遗留与后续建议

1. **P3-10（版本耦合）**：未改代码，已说明理由。建议在下次升级 Spring AI 时把 `PersistentSimpleVectorStoreTest` 列为必跑回归。
2. **`AgentTools.getMyInterviewStats` 仍走 `questionSummary`**：该工具需要 `answeredQuestions` 与 `byDifficulty`，而轻量画像不提供这两项，强行替换会造成**功能性退化**，故保留。因其由工具调用按需触发（非每轮），影响有限；后续如需优化，应补 `answeredCount` / `difficultyStats` 两个聚合查询。
3. **P2-9 契约尚未在代码层强制**：当前以文档固化规则。若要彻底消除歧义，需统一返回形态（改动面覆盖全部控制器 + 前端拦截器 + 数百项断言），建议作为独立迭代立项，不在本次范围内。
4. **前端未做功能改造**：本次全部修复均在后端，前端**零改动**（P2-10 为新增字段、P2-9 仅文档），故前端测试保持 282 项不变。
5. **生产环境未复测**：本地 `local` profile（H2 + 内存向量库 + 无 Redis）。其中 **P2-5 的兜底缓存路径、P3-9 的新增 JPQL 聚合、P2-1 的 multipart 语义**建议在下次发布前于生产（PostgreSQL + PgVector + Redis）复验一遍。
6. **端到端复测建议**：P1-1 涉及真实第三方抓取（本轮仅单测覆盖），建议在生产观察联网招聘源的来源分布是否确实出现多源结果。
