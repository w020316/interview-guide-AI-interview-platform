# 阶段一交付物 · 功能缺口报告（offerGo v1.89.0）

> 审查对象：`interview-guide/`，基线 `3f354a4`（v1.89.0）
> 判定口径：**「后端有能力 / 前端无入口」或「用户旅程断点在产品层」** 才算缺口；纯技术缺陷归 [01-问题清单.md](./01-问题清单.md)。
> 结论先行：缺口共 **11 项**，其中 **3 项属于"承诺了但没做到"（P1 级体验债）**，4 项为"半成品"（API 有、UI 无），4 项为能力空白。

## 2. 逐项分析

### G-01 知识库文档无法删除（API 有、UI 无）· 优先级 P1

**现状**
- 后端：`KnowledgeController.java:309` `@DeleteMapping("/{docId}")` 已实现（含归属校验）。
- 前端：`KnowledgeView.vue` 只有上传、列表、检索、错题本，**没有任何删除入口**；`KnowledgeView.vue:510-524` 的 `loadWrong` 也没有单条删除。

**为什么是 P1**
知识库是"上传即入库"的语义。用户传错文件（传了别人的简历、传了含隐私的合同）后**无法撤回**，只能看着它出现在每次检索结果里。这既是体验问题，也是隐私问题——而删除能力后端已经写好了，纯粹是前端漏了入口，投入产出比最高。

**建议方案**
1. 列表项加"删除"图标 + `ElMessageBox.confirm`（对齐 P2-20 的统一确认组件）。
2. 删除后局部刷新列表与统计（当前 `loadSummary` 独立请求，注意联动）。
3. 批量删除：列表支持多选 + 顶部"删除选中"（后端需补批量端点，或前端串行调用）。
4. 错题本同样补删除（后端对应端点需确认，若无则先只做文档删除）。

**验证**：上传 → 删除 → 列表消失、检索不再命中、刷新页面仍消失。

---

### G-02 岗位详情页缺失（API 有、无路由）· 优先级 P1

**现状**
- 后端：`JobAgentController.java:176` `@GetMapping("/{id}")` 返回完整岗位详情（描述、要求、标签、公司信息）。
- 前端：`JobsView.vue` 是卡片列表 + 右侧抽屉（仅摘要字段），**没有 `/jobs/:id` 路由**，`raw/frontend-api-calls.json` 中无该路径调用。

**为什么是 P1**
1. 卡片上只能放 200 字摘要，长 JD 被截断，用户无法判断"要不要投"。
2. 详情页是 SEO/分享的自然落点（当前分享岗位只能分享列表页，落地后还得自己找）。
3. 后端已实现且有测试，前端补一个页面即可，属于"低成本补齐主旅程"。

**建议方案**
1. 新增路由 `/jobs/:id`（`requiresAuth: false`，公开可看，投递/收藏时再要求登录）。
2. 页面结构：标题区（岗位/公司/薪资/地点）→ 标签 → JD 正文（保留换行）→ 要求 → 公司信息 → 底部固定操作条（收藏 / 去投递 / 生成求职信）。
3. 列表卡片标题改为可点击跳详情；"去投递"按钮保留直接外链（高频路径不增加点击）。
4. 详情页补 `document.title` 与 `og:` meta（分享友好）。

**验证**：列表点标题 → 详情 → 返回列表位置保持；未登录点"收藏"→ 跳登录并回跳详情页。

### G-03 备份「包含对话记录」是假开关 · 优先级 P1

**现状**
- `BackupService.java:117-166`：`includeConversations` 只被读入、在响应里原样回显（`:161`），**没有任何对话仓储被调用**。
- `MeController.java:58-60`：把参数透传下去。
- 前端设置页有该勾选项。

**为什么是 P1**
"看起来生效了"比"没有这个功能"更糟：用户以为备份完整，实际换机/清库后对话全丢。属于承诺未兑现，且是数据安全类承诺。

**建议方案（二选一，推荐 A）**
- **A. 实现**：导出 `agent_conversations` + `agent_messages`（按时间倒序取最近 N 条，避免 P2-10 的无上限问题），导入时按 id 去重合并。
- **B. 移除**：删掉前端勾选项与后端参数，避免假承诺。

**验证**：勾选导出 → 解压/解析 JSON 含对话 → 导入新账号 → 对话可见。

### G-04 待办事项只能看不能关 · 优先级 P2

**现状**
岗位详情/投递流程会生成建议待办（如"3 天后跟进"），前端展示为清单，但**后端没有完成/忽略的写接口**，也无 `completed_at` 列。

**为什么是 P2**
不做的话"待办"永远是只读展示，用户第二次看到就无视它了，功能形同虚设。

**建议方案**
1. `SchemaInitializer.DDL_LIST` 增加 `todo_item` 表（id/user_id/title/due_at/done_at/source_type/source_id）。
2. 端点：`GET /api/todos`、`PATCH /api/todos/{id}`（done/undone）、`DELETE`。
3. 前端：Dashboard 待办卡支持勾选，已完成折叠。

**验证**：勾选 → 刷新仍为已完成；跨设备一致。

---

### G-05 站内提醒 / 面试倒计时缺失 · 优先级 P2

**现状**
日历能记录面试时间，但没有提醒：不打开网站就不知道明天有面试。PWA 已具备（`vite-plugin-pwa`），但未使用 Notification / 本地通知。

**建议方案（分两步，先做零成本版）**
1. **零后端版**：进入站点时检查未来 24h 面试，`ElNotification` 提醒 + 日历页顶部倒计时条；PWA 安装用户可用 `showNotification`（需用户授权）。
2. **可选增强**：Service Worker `periodicSync`（浏览器支持有限，仅作增强，不作承诺）。

**验证**：造一条 2 小时后的面试 → 刷新首页 → 出现提醒；点提醒跳日历。

---

### G-06 账号找回 / 忘记密码缺失 · 优先级 P2

**现状**
`AuthController` 只有注册/登录/改密/登出，**没有忘记密码**。密码一忘，账号永久不可用（管理员也只能改角色/封禁）。

**为什么是 P2 而非 P1**
当前是邀请/自注册的小规模产品，用户可用新账号；但一旦对外，这是硬伤。且实现需要邮件通道（Resend/SMTP），涉及外部依赖与配置，故排 P2。

**建议方案（最小闭环）**
1. `POST /api/auth/forgot-password`：生成一次性 token（Redis，15 分钟，单次使用），发邮件。
2. `POST /api/auth/reset-password`：校验 token → 改密 → `incrementTokenVersion` 使旧会话全下线。
3. 防枚举：无论邮箱是否存在都返回同一文案。
4. 邮件服务未配置时，该入口隐藏（不展示不可用功能）。

### G-07 封禁状态不落库 · 优先级 P1（并入 P2-14）

已在问题清单 P2-14 详述：`UserBanRegistry` 仅 Redis + 内存，Redis 重启/写失败即失效。功能上"封禁"这个管理能力是不可靠的，属缺口；技术修复归 P2-14。

---

### G-08 自持 AI Key 无法"只改模型不改 Key" · 优先级 P2

**现状**
`MeController.java:104-110` 要求 `apiKey` 必填；`UserAiKeyService.java:88-99` 每次更新都重新加密。用户想从 `gpt-4o-mini` 换到 `gpt-4o`，必须重新粘贴 Key。

**方案**：`apiKey` 改为可选；为空时保留原密文，仅更新 model/baseUrl；前端显示"已配置（sk-****1234）"与"更换 Key"两个动作。

### G-09 两个死端点 · 优先级 P3

| 端点 | 状态 | 处置 |
|---|---|---|
| `GET /api/jobs/favorite/ids`（`JobAgentController.java:344`） | 前端未调用（岗位收藏走 `GET /api/favorite/ids`） | 删除，或补"收藏岗位"筛选时启用 |
| `GET /api/knowledge/recent-questions`（`KnowledgeController.java:269`） | 前端未调用 | 若"最近提问"有价值则接入首页；否则删除 |

### G-10 报告分享形态不完整 · 优先级 P2

**现状**
复盘报告支持页面查看与 PDF 打印（`reportPdf`），但分享链接的有效期/撤销语义不清晰（P3-21 记录了撤销时机问题），且分享页无"对方视角"的只读布局校验。

**建议**：分享链接显式展示"有效期至 X"、支持手动撤销；分享页隐藏所有编辑入口与个人设置入口。

---

### G-11 岗位收藏无独立入口 · 优先级 P2

**现状**
岗位可收藏（`/api/favorite/ids`），但"我的收藏"只出现在投递看板的筛选里，没有一个"收藏的岗位"列表页。用户收藏 30 个岗位后无法集中管理（取消收藏要逐个回到列表找）。

**建议**：`/jobs?favorite=1` 支持收藏筛选（复用现有列表），或在"我的"页加"收藏的岗位"卡片入口。

## 3. 缺口与阶段六的关系

用户已确认阶段六要"继续调研同类型开源项目，完善项目，完善功能"。上述缺口中，**G-01 / G-02 / G-03 建议在阶段二就做**（成本低、属补齐而非新增），理由：

1. 三者都是"后端已完成、只差最后一公里"，不需要产品决策，也不引入新依赖。
2. 若留到阶段六，会与"调研后新增功能"混在一起，难以判断哪些是补债、哪些是创新。
3. G-01（删除）与 G-03（备份真实性）都涉及数据主权，属质量底线。

阶段六的调研将聚焦"同类型产品的差异化能力"（如模拟面试的多模态评分、岗位匹配的可解释性、求职漏斗分析），而不是重复本报告已识别的补债项。

## 4. 不计入缺口的项（避免误判）

| 项 | 不计入原因 |
|---|---|
| `/api/health`、`/api/health/detail` 无前端入口 | 运维端点，设计如此 |
| 无 Pinia / 无全局状态库 | 架构选择，当前模块级 `reactive` 已满足，非缺口 |
| 无国际化 | 产品定位中文用户，非承诺功能 |
| 无移动端 App | 产品定位 Web/PWA，非承诺功能 |
| 管理端无审计日志页 | 后端有日志，但无"操作审计"承诺；若阶段六调研认为必要再立项 |
