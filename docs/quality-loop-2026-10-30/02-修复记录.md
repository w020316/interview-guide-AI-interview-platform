## 2. P1 修复记录（6/6）

### P1-01 登录限流维度拆分 + 受信代理配置

- **原始问题**：生产 `remoteAddr` 是网关公网 IP，`ClientIpUtil` 不解析 XFF → 全站共用 IP 桶；
  阈值 5 时任意人连错 5 次即可锁死全站登录 5 分钟。
- **技术方案**：
  1. IP 维度降级为粗粒度防刷（默认 50 次 / 1 分钟锁），账号维度保持 5 次 / 5 分钟（真正防线）；
     全部阈值可配置（`app.auth.login-ip-max-fail` 等）。
  2. 登录失败日志记录「解析后 IP + 原始 XFF（截断 200 字符）」，为实测边缘网段提供线索。
  3. `application.yml` 新增 `app.security.trusted-proxy-prefixes`（env `APP_SECURITY_TRUSTED_PROXY_PREFIXES`），
     `render.yaml` 以 `sync: false` 交付面板维护。
- **验证**：新增「同一 IP 下 5 个不同账号各错一次不触发全站锁定」用例（AuthControllerTest）；
  ClientIpUtilTest 11 条仍全绿。
- **未做/边界**：**未对 Render 生产发起探针**（遵守额度纪律），因此边缘网段仍未取证；
  保底方案（维度拆分）独立成立，取证后只需回填面板变量。

### P1-02 匿名访客被踢登录

- **技术方案**：新增 `utils/publicRoutes.ts`（受保护路径清单；未匹配路径即 404 视为公开）；
  `evaluateSessionRecovery` 增加公开性判定，新增 `clear-and-stay` 动作：
  公开页脏 token 只静默清理，不跳转、不提示。
- **验证**：sessionGuard 新增 7 条公开路由用例 + publicRoutes 6 条；合计 28 条通过。

### P1-03 登出未吊销 token

- **技术方案**：新增纯函数 `logoutRequestConfig(token)`，登出时**显式**把旧 token 放进请求头，
  再清本地状态并跳转；不再依赖请求拦截器读 localStorage 的时序。
- **验证**：logout.test 2 条；后端 logout 行为未变（已有 3 条用例覆盖认证/匿名路径）。

### P1-04 applyUrl 协议白名单

- **技术方案**：新增 `UrlSafety`（只放行 http/https 且 host 非空，按码点限长 500），
  在岗位入库、台账/收藏入账、Excel 导入、applyKit/时间线/收藏列表**读侧**统一过滤；
  前端新增 `safeExternalUrl`，在 Jobs/Favorites/Application 三处 href 与 `window.open` 前再过滤。
- **验证**：UrlSafetyTest 17 条（含大小写、前导空白、控制字符、data/blob/file/vbscript）；
  safeLink.test 11 条；vue-tsc 0 error。

### P1-05 自持 Key 在流式链路失效

- **技术方案**：
  1. 两处 SSE 线程池改为 `DelegatingSecurityContextExecutorService`（提交时捕获上下文）。
  2. 新增 `SecurityContextPropagation`，`AgentService.runStream` 与标题生成在任务体内
     设置/还原上下文（Reactor 的 `subscribeOn` 会再次换线程，委托执行器覆盖不到）。
  3. `SelfKeyAwareChatModel.stream()` 与非流式对称：用户 Key 生效，失败转 `BusinessException`
     且**不回落平台链**。
- **验证**：SelfKeyAwareChatModelTest 7 条（含 2 条新增 stream 用例）；
  SecurityContextPropagationTest 2 条（先复现裸线程丢上下文，再验证搬运/还原）。

### P1-06 评估切题污染答题记录

- **技术方案**：`await` 前 `snapshotQuestion()` 快照题面/题号/作答；
  请求体改由纯函数 `buildEvaluateBody` / `buildSessionAnswerBody` 构造（从结构上杜绝再读响应式状态）；
  `evalLoading` 期间禁用「跳过/下一题」，`nextQuestion()` 内兜底 `return`。
- **验证**：interviewAnswer.test 6 条（含「切题后 questionId 仍取快照值」）。

### 3.1 P2-09 补充修复（B7，`658ff01`）

- **原始问题**：`BusinessException` 被全局处理器统一映射成 **503「服务暂不可用」**。
  故事库「已满（上限 50 条）」是用户正常操作触发的资源冲突、「标题不能为空」是请求参数错误，
  两者都被报成服务端故障，用户会以为平台坏了而放弃操作。
- **技术方案**：给 `BusinessException` 增加 `status` 载体（默认 `DEFAULT_STATUS = 503`，
  AI 全链失败、并发闸门超时等历史契约不变）；抛出方显式声明语义 —— 配额 → `409`、空标题 → `400`。
  `GlobalExceptionHandler#handleBusiness` 由固定 `@ResponseStatus` 改为 `ResponseEntity` 输出动态状态码，
  body 的 `code` 与 HTTP 状态码同源，杜绝二者不一致。
- **影响面控制**：只有 `StoryBankService#save` 两处改用带状态码的构造器，其余抛出点行为零变化；
  既有 `AuthChangePasswordTest` 的「未认证 → 503」用例仍绿，证明默认契约未被破坏。
- **验证**：`GlobalExceptionHandlerTest` 覆盖 503（未声明）/ 409 / 400 三分支；
  `StoryBankServiceTest` 两条用例追加 `getStatus()` 断言（400 / 409 且文案正确）；
  后端全量 `mvn -B -ntp test` → **1635 用例 / 0 失败 / BUILD SUCCESS（JaCoCo 门禁通过）**。
- **断言变更说明**：`handleBusiness` 返回值类型由 `Result<Void>` 改为 `ResponseEntity<Result<Void>>`，
  对应 1 条既有用例按新契约改写（属**契约有意变更**，非为绿灯放宽断言）。
