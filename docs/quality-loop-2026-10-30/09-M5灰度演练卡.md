# M5 灰度与回滚演练卡

**适用版本**：`5c8097a` 及以后（三条 P1 已闭环：`e24c1b4` / `a1eb21c` / `d71df1d`）
**前置**：Render Dashboard 权限 + Supabase SQL Editor 权限；建议选低峰时段（一次演练约 20 分钟，含 2 次冷启动）
**开关**：`APP_TASK_CENTER_ENABLED`，当前 `render.yaml` 显式 `false`

> ⚠️ **这不是热切换**。改环境变量必须重启，冷启动实测 209–488s，期间服务不可用。
> ⚠️ **重启会硬杀在途任务**（`@PreDestroy` 的 `shutdownNow()`）。这正是本卡要验的东西。

## D0 · 建表核查（2026-10-31 首次演练时发现并修复了一个 P0）

> **结论：`ai_task` 表此前在生产根本不存在。** 这条是演练的第一个战果——如果不做演练直接开开关，用户看到的是全线 500。

| 项 | 内容 |
|---|---|
| 现象 | `GET /api/tasks` 返回 `{"code":500,"message":"数据库操作失败，请联系管理员"}` |
| 根因 | `CREATE TABLE ai_task` 只写进了 `schema.sql`，没进 `SchemaInitializer.DDL_LIST`；而 prod 是 `sql.init.mode=never` + `ddl-auto=none` → 生产库从未建过这张表 |
| 影响 | **开关一开，所有任务接口都会 500**（不是降级，是彻底不可用） |
| 修复 | `291d977`：补 DDL + 纳入 `REQUIRED_TABLES` 启动自检 + 新增 `SchemaDdlCoverageTest` 门禁（扫实体自动发现，变异测试验证过会红） |
| 复核 | 部署后 `GET /api/tasks` 由 500 → 200（2026-10-31 12:40 实测），指纹成立 |

**开灰度之前先跑这条**：

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  https://interview-guide-backend.onrender.com/api/tasks
# 必须 code=200
# 若为 500：表又没建成 —— 去看启动日志里的 REQUIRED_TABLES 自检（它会打 ERROR 点名缺哪张表）
```

## D1 · 开灰度（约 8 分钟）

1. Render Dashboard → `interview-guide-backend` → Environment → 新增
   `APP_TASK_CENTER_ENABLED` = `true` → 保存（自动重启）。
2. 轮询健康检查，直到 `UP`：

```bash
curl -s https://interview-guide-backend.onrender.com/actuator/health
# 期望：{"status":"UP"}
```

3. 登录拿 token（`data` 是**裸 token 字符串**，不是对象）：

```bash
curl -s -X POST https://interview-guide-backend.onrender.com/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"ux3_user","password":"Ux3@Test2026"}'
# 期望：{"code":200,"data":"eyJhbGciOi..."}
```

4. 三个接口的开关语义必须**同时**成立：

```bash
TOKEN=<上一步的 data>

# ① 列表：开关开 → 200（不是 503）
curl -s -H "Authorization: Bearer $TOKEN" \
  https://interview-guide-backend.onrender.com/api/tasks
# 期望：{"code":200,"data":{"items":[...],"total":N,...}}

# ② 创建：开关开 → 200 + taskId
curl -s -X POST https://interview-guide-backend.onrender.com/api/tasks/interview/questions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"resumeText":"Java 后端 5 年，熟悉 Spring Boot 与 MySQL","jobDescription":"Java 后端工程师","count":3}'
# 期望：{"code":200,"data":{"taskId":<ID>,"status":"QUEUED"}}

# ③ 汇总：开关开 → 200
curl -s -H "Authorization: Bearer $TOKEN" \
  https://interview-guide-backend.onrender.com/api/tasks/summary
```

**通过判据**：① ② ③ 全部 `code=200`。任一为 503 → 环境变量没生效，回 D1 步骤 1 检查拼写。

## D2 · 冒烟（约 5 分钟）

等 30–90s（单任务串行调度 + AI 出题实测 77s），然后：

```bash
# 任务应已 SUCCEEDED
curl -s -H "Authorization: Bearer $TOKEN" \

  https://interview-guide-backend.onrender.com/api/tasks/<taskId>/result
# 期望：data.resultText 是题目 JSON 数组
```

**浏览器走查（这一步不能省，接口绿不代表用户能用）**：
1. 打开 `https://offergo.pages.dev` → 模拟面试 → 开始面试（允许它转后台任务）
2. **立刻切走页面**（切标签 / 关页面都行）
3. 回来看头像菜单「我的任务」→ 该任务显示「已完成」
4. 点「去看看」→ **必须直接看到题目列表**（这是 P1-2 的验收点，看不到就是没修好）
5. 再点「重新生成」→ 应拿到**不同**的一批题（这是 P1-3 的验收点）

**通过判据**：4 与 5 都成立。4 失败 → 立即执行 D3 回滚。

## D3 · 回滚（约 8 分钟，三步不可颠倒）

**第一步：先记账**（重启会硬杀在途任务，必须留证据）

```sql
-- S1 回滚前快照
SELECT id, user_id, type, attempt, max_attempt, started_at
FROM ai_task WHERE status = 'RUNNING' ORDER BY id;
```

把结果存到本地（截图或复制）。**预期 0 行**——如果恰好有行，正好用它验证收敛。

**第二步：关开关 + 重启**

Render Dashboard → `APP_TASK_CENTER_ENABLED` 改为 `false` → 保存（自动重启）。
等 `/actuator/health` 回到 `UP`（又是 4–8 分钟）。

**第三步：验证收敛（P1-1 的核心）**

```sql
-- S2 重启后复核：必须全为 0
SELECT count(*) FROM ai_task WHERE status IN ('RUNNING', 'QUEUED');
```

> 从 `e24c1b4` 起，**这件事由启动收敛自动完成**：开关关闭时 `ApplicationReadyEvent`
> 会把未结束任务全部置为 `FAILED + error_code='ROLLBACK'`。
> **S2 为 0 是"收敛生效"的证据；不为 0 说明收敛没跑起来 —— 记缺陷，别只手工修数据。**

**第四步：确认前端回到同步链路**

```bash
# 创建接口应恢复 503
curl -s -X POST https://interview-guide-backend.onrender.com/api/tasks/interview/questions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"resumeText":"x","jobDescription":"y","count":3}'
# 期望：{"code":503,"message":"任务中心未启用"}

# 但列表/取消仍可用（P1-1 的另一个验收点）
curl -s -H "Authorization: Bearer $TOKEN" \
  https://interview-guide-backend.onrender.com/api/tasks
# 期望：{"code":200,...} —— 不是 503
```

浏览器：再走一次「开始面试」，应**直接**出题（走同步接口），无 503 报错、无「已转后台任务」提示。

**通过判据**：S2 全 0 + 创建 503 + 列表 200 + 浏览器同步出题正常。

## D4 · 收尾

| 项 | 动作 |
|---|---|
| 兜底 SQL | **仅在 S2 不为 0 时执行**（说明收敛失效），执行后必须记一条缺陷 |
| 用户可见性 | 若 D3 前有 RUNNING 任务，对应任务的用户会在「我的任务」看到「任务中心已回滚，请重新发起」 |
| 数据清理 | **不要 DELETE** —— 这些行是前端「去重新发起」的落点，30 天后由清理任务自动回收 |
| 记录 | 填下面的记录表，结论写进交接单 |

```sql
-- 兜底（正常情况下不该执行）
UPDATE ai_task
   SET status='FAILED', error_code='ROLLBACK',
       error_message='任务中心已回滚，请重新发起',
       finished_at=now(), lease_until=NULL, progress=0
 WHERE status IN ('RUNNING','QUEUED');
```

## 中止条件（命中任一，立即执行 D3）

- `/actuator/health` 10 分钟未 `UP`
- 创建任务后 **5 分钟**仍为 `QUEUED`（调度器没跑 → 查 `app.task-center.poll-interval-ms` 与日志里的领取异常）
- 任务卡在 `RUNNING` 超过 **4 分钟**（租约 180s + 余量，说明执行线程死了）
- 任何接口出现 5xx 或前端出现「任务中心未启用」以外的报错
