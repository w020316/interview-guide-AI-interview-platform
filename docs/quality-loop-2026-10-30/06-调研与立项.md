## 1. 引言与问题背景

阶段四实测出一条明确的 P2（E-06）：

| 事实 | 数据 |
|---|---|
| 出题接口 | `POST /api/interview/questions` **77.1s**（端到端 108s） |
| 单题评分 | **11.6 / 24.9 / 26.9s**（同一题三次独立评分） |
| 用户感知 | 只能盯着进度条，无法离开页面；失败后要重新录入 |

平台当前形态：**Spring Boot 单实例**部署在 Render 免费层，Redis 可选、无独立 worker 进程。任何「引入队列」的方案都必须先回答一个问题：**在只有 1 个实例、且会被休眠的环境里，额外的 broker / worker 是否值得。**

本案即为该问题的调研与立项。

## 4. SWOT 分析

### 4.1 引入成熟队列（以 BullMQ / Celery 为代表）

| | 内容 |
|---|---|
| **S** 优势 | 重试、退避、并发控制、可视化成熟；社区大、案例多 |
| **W** 劣势 | 需要 broker + 独立 worker（Render 免费层无法常驻）；与 Java 服务跨语言集成，多一套运行时 |
| **O** 机会 | 未来若迁到付费层、需要多实例消费时，可直接复用 |
| **T** 威胁 | 免费层休眠导致 worker 与 web 同生共死；broker 内存挤占 220–512MB 限额 |

### 4.2 自建任务表 + 单实例调度

| | 内容 |
|---|---|
| **S** 优势 | 零新基础设施（复用现有 PostgreSQL/H2 + Spring `@Scheduled`）；任务状态可查询、可取消、可幂等；与现有鉴权/限流/审计天然一致 |
| **W** 劣势 | 多实例时需处理抢占（可用 `FOR UPDATE SKIP LOCKED`，当前单实例不涉及）；无可视化运维面板 |
| **O** 机会 | 先把「异步化 + 可恢复」跑通，后续若扩容可平滑替换为 Quartz（DB JobStore）或外部队列 |
| **T** 威胁 | 任务表膨胀、重复执行、AI 配额被后台任务吃满 → 需清理策略与配额隔离 |

**结论**：当前阶段选 4.2。理由不是「自研更酷」，而是**运维条件约束**：单实例 + 免费层不常驻 worker，引入 broker 的收益无法兑现。

**最终结论**：
1. 本轮**自建**（不引第三方依赖），因为需求只有「异步执行 + 可查询 + 可重试 + 可取消」；
2. Quartz 作为**演进备选**登记：若后续需要多实例抢占或 cron 表达式，迁移成本最低（同 JVM、Apache-2.0、DB JobStore）。

## 6. 方案设计

### 6.1 模块划分

| 模块 | 职责 | 落点 |
|---|---|---|
| `AiTaskEntity` | 任务持久化（状态机、进度、重试计数、幂等键） | `entity/` |
| `AiTaskService` | 创建 / 查询 / 取消 / 心跳 / 清理 | `service/task/` |
| `AiTaskRunner` | 按类型分派执行器（出题、评分、简历分析…） | `service/task/runner/` |
| `AiTaskScheduler` | 单实例轮询领取任务（`@Scheduled` + 乐观锁抢占） | `service/task/` |
| `AiTaskController` | REST：创建 / 查询 / 取消 / 列表 | `controller/` |
| 前端 `TaskCenter` | 任务列表 + 进度 + 「完成提醒」 | `frontend/src/views/`（复用 Drawer） |

### 6.2 接口定义（草案）

| 方法 | 路径 | 语义 | 关键字段 |
|---|---|---|---|
| POST | `/api/tasks` | 创建任务 | `type`、`idempotencyKey`、`payload` → `taskId`、`status=QUEUED` |
| GET | `/api/tasks/{id}` | 查询单个 | `status`、`progress`、`resultRef`、`error` |
| GET | `/api/tasks?status=&type=&page=` | 我的任务列表（仅本人） | 分页 |
| POST | `/api/tasks/{id}/cancel` | 取消（仅 QUEUED/RUNNING 且本人） | 幂等：重复取消返回当前态 |
| GET | `/api/tasks/summary` | 未完成/失败数量（红点与导航角标） | `queued`、`running`、`failed` |

> 鉴权：沿用现有 JWT；`userId` 一律从 SecurityContext 取，**不接受请求体传入**（防 IDOR）。
> 结果获取：沿用既有 `resultRef`（如会话/简历 ID），**任务表不存大文本**，避免表膨胀。

### 6.3 数据模型（草案）

```sql
CREATE TABLE ai_task (
  id              BIGSERIAL PRIMARY KEY,
  user_id         BIGINT      NOT NULL,
  type            VARCHAR(32) NOT NULL,          -- interview.questions / interview.evaluate / resume.analyze
  idempotency_key VARCHAR(96) NOT NULL,          -- 同用户同键只允许一条有效任务
  status          VARCHAR(16) NOT NULL,          -- QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED
  progress        SMALLINT    NOT NULL DEFAULT 0,
  attempt         SMALLINT    NOT NULL DEFAULT 0,
  max_attempt     SMALLINT    NOT NULL DEFAULT 1,
  payload         TEXT,                          -- 入参快照（脱敏后）
  result_ref      VARCHAR(64),                   -- 结果引用，不存正文
  error_code      VARCHAR(32),
  error_message   VARCHAR(200),
  lease_until     TIMESTAMP,                     -- 抢占租约，防重复执行
  created_at      TIMESTAMP   NOT NULL,
  started_at      TIMESTAMP,
  finished_at     TIMESTAMP
);
CREATE UNIQUE INDEX uk_ai_task_idem ON ai_task (user_id, idempotency_key)
  WHERE status IN ('QUEUED','RUNNING','SUCCEEDED');  -- H2 需降级为普通唯一索引 + 应用层判断
```

### 6.4 架构（部署视角）

```
浏览器
  │  POST /api/tasks（幂等键）
  ▼
Spring Boot 单实例 ─────────────┐
  ├─ AiTaskController → AiTaskService → ai_task 表
  ├─ AiTaskScheduler（@Scheduled 每 5s）── 领取 QUEUED（租约 60s）
  │      └─ AiTaskRunner（虚拟线程池，AI 闸门限并发）
  │            ├─ 成功：progress=100 / result_ref
  │            └─ 失败：attempt+1 ≤ max_attempt → 退避重排；否则 FAILED
  └─ 通知：轮询 GET /api/tasks/summary（前端 30s/次，页面可见时）
       ▲
       └── 复用既有 PostgreSQL（本机 H2），**不新增 broker/worker**
```

### 6.5 状态机

`QUEUED → RUNNING → SUCCEEDED | FAILED`；`QUEUED/RUNNING → CANCELLED`；
`FAILED → QUEUED`（仅手动重试，attempt 未超上限）。

## 7. 技术栈选型理由

| 选择 | 理由 |
|---|---|
| 复用 PostgreSQL/H2 而无 broker | 免费层单实例，broker 的内存与常驻进程不可得；任务量级（单人单次面试 3–5 个任务）远未到队列系统必要阈值 |
| Spring `@Scheduled` + 租约 | 与现有 `JobRefreshScheduler` 同一模式，团队认知成本为零 |
| 虚拟线程池 + 既有 `AiConcurrencyGuard` | 复用现有 AI 并发闸门与限流，避免后台任务打爆厂商 RPM（阶段二 P1-05 已验证上下文传播） |
| 前端轮询而非 SSE | SSE 仅用于需要 token 级流式的对话；任务中心只需状态，轮询更省连接与配额 |
| 不引入 Quartz | 当前无 cron/集群需求；登记为演进备选（评分 4.4 最高，但收益不成立） |

## 8. 核心实现思路

1. **幂等**：同用户 + 同 `idempotencyKey` 已有 QUEUED/RUNNING/SUCCEEDED 时直接返回原任务，避免用户连点产生多份 AI 计费。
2. **抢占与租约**：`UPDATE ... SET status='RUNNING', lease_until=now()+60s WHERE id=? AND status='QUEUED'`，受影响行数为 1 才执行；进程崩溃后租约到期由下一轮重新领取。
3. **失败语义**：沿用阶段二 P2-09 的 `BusinessException(status)`；对上游 429/1305 记为 `RETRYABLE` 并按指数退避（1s/2s/4s），对 4xx 配置错误不重试。
4. **结果不落大文本**：任务只存 `result_ref`（会话 ID / 简历 ID），正文仍写业务表。
5. **配额隔离**：后台任务走 `AiConcurrencyGuard` 的后台许可（现为 2），保证前台请求优先。
6. **清理**：`SUCCEEDED/CANCELLED` 保留 7 天、`FAILED` 保留 30 天，由每日 03:00 任务清理（与现有调度同族）。
7. **可观测**：`/api/tasks/summary` 暴露排队/运行/失败数；日志统一带 `taskId` 与 `type`，便于按任务串联。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 单实例休眠导致任务停滞 | 用户看到「排队中」不动 | 前端提示「实例休眠时任务会延后」；上线后观察 Render 唤醒耗时，必要时在唤醒时主动 kick 一次调度 |
| 租约内执行超过 60s（AI 出题实测 77s） | 任务被判超时重排，可能重复执行 | 租约按时长分档（出题 180s / 评分 120s）；执行器每 30s 续租 |
| 任务表膨胀 | 查询变慢、备份变大 | 清理任务 + 索引 `(user_id, created_at)`；payload 仅存必要字段 |
| 后台任务吃满 AI 配额 | 前台 429/503 | 后台独立许可 + 每用户后台任务并发上限 1 |
| 幂等键冲突策略不清 | 重复计费或误复用 | 明确规定：同键仅复用「未失败」任务；失败后同键允许新建 |
